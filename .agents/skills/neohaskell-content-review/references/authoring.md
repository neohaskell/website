# Author a complete documentation page

Use the current ticket for scope and `AGENTS.md` for delivery. This reference owns teaching and source practice, not the page queue or server lifecycle.

## Establish the page's job

Read `PRODUCT.md`, `GLOSSARY.md`, the existing page, and the relevant learning path from [reading context](reading-context.md). The four introductory lessons are the teaching and philosophical baseline. Resolve page order from the current navigation and ticket rather than inventing a new curriculum.

Write the reader's immediate goal and the visible result that completes it. Keep the material that serves that result. A creation page ends with a recognizable project; running the application and tracing all its files belong to their own pages. Mention supporting tools only as far as the task needs them. It is useful to say that Neo initializes Git and commits the generated files; a project-creation lesson does not need Git inspection commands, identity configuration, or a version-control tutorial. Apply the same boundary to Nix, build tools, editors, and other supporting tools. Keep detailed verification in internal evidence unless the reader needs it to complete the NeoHaskell task. For a conceptual lesson, state the question the reader should be able to reason about afterward.

When revising, preserve useful explanations and accepted choices outside the correction. When deleting, inspect incoming links, stable anchors, navigation, and the explanation that used to supply a prerequisite. Repair those dependencies within scope or report the concrete gap. Translation remains separately authorized.

## Investigate the actual path

Follow a command or API through its entry point, implementation, generated artifacts, and relevant tests. Read source-repository instructions before inspection. Confirm which source revision the reader's tool or starter actually uses. A local checkout, a published CLI, and the framework pinned by a generated project can all differ. Read generated files rather than treating a template or historical research as their contents.

For installation lessons, inspect the shipped bootstrap, lifecycle dispatcher, shell setup and English messages at the published revision. Distinguish prerequisites from tools the installer supplies, paired command versions from project pins, and removal of package-retention links from deletion of package contents. Verify the public download and compare version checks with the release manifest. Passing asset checks, fixtures and private-cache runs do not establish a clean-host install, update or uninstall; record that evidence boundary internally. Keep supporting package-manager details in linked setup guidance unless they affect a reader decision.

For agent setup, distinguish shared workflow skills from API guidance matched to the project's effective framework source. Inspect the documented CLI's maintained installer before adding a separate installation tool. Verify installed instructions in an isolated project, including their destination and the active guidance index, rather than treating an installer success message as the whole result.

For troubleshooting, reproduce the symptom through the reader's actual command in an isolated project. Compare the observed diagnostic with the underlying source before choosing a fix, since a declared error may never appear on that path. Record controlled failure conditions and remove them for the recovery check. Teach the smallest correction that preserves the project, paired with the first visible result that confirms recovery.

Run the documented path in an isolated directory when tools permit. Verify every displayed command and claimed result. An interactive route needs its prompts checked; a noninteractive route needs its flags and defaults checked. Avoid environment overrides that make a check pass without exercising the reader's path. Preserve failures as evidence and investigate their cause before choosing a workaround.

For a running-service lesson, verify readiness with a real request, then exercise stopping and restarting the process. Download progress, a compilation success, a startup log, or a test that merely times out cannot establish that the server answers. Check optional modes against their implementation and observed behavior too; a help message promising automatic restart is not evidence that restart occurs. Keep the working path in the article and record unsupported optional behavior for its owning ticket. If that behavior is necessary to the page's stated result, treat it as a blocker.

For transport configuration, follow settings through application startup as well as the transport record. Application-level configuration may replace transport defaults; verify browser-origin permissions with an allowed and an unlisted origin before teaching the declaration. Explain configuration transitions through the actual imports, registrations, settings and factory types to change. Do not teach swapping whole source files through cp commands or backup-file variants. Preserve unrelated work through a focused diff and keep deployed domain files unchanged.

For stdio transports, verify the launch path preserves standard input and keeps protocol output separate from routine logs. Exercise initialization, discovery, a real command and a query read. Check resource parameters against the transport implementation rather than assuming parity with HTTP, and distinguish trusted command execution from query access policy.

For application CLI lessons, verify argument ownership before the transport runs, generated entity groups and field flags, and every declared transport registration. Exercise process exit, retained history across invocations, actual output switches and domain rejection exit status before teaching scripting. Distinguish the development CLI from the application interface.

For storage lessons, distinguish retained event history from stored query rows and asynchronous query reconstruction. Verify the same entity and query before and after a real process restart, without reopening the entity or deleting history. Inspect every required backend configuration field at the pinned revision; starter comments can lag behind the API. A compiled database configuration is not evidence of a successful database connection or retained volume. Inspect each builder signature separately: an event-store factory does not establish that a query-store setting also accepts a factory. When continuing a prior exercise, use its final state rather than its opening state; choose a fresh entity in the retained history when a new accepted action needs stock, without deleting prior events.

For file-storage lessons, trace a reference through the actual command pipeline before promising ownership resolution or confirmation. A route-handler definition does not prove the application calls it. Verify expiry separately from physical cleanup, including whether startup launches the worker. Keep file bytes, lifecycle metadata and application history separate in persistence explanations. Check same-owner content deduplication before promising a new reference or renewed expiry on re-upload. For generated documents, exercise first completion, repeated creation, conflicting metadata, missing-blob repair, and failure of the receiving completion command separately. An existing retained blob may preserve the first bytes without comparing replacement bytes; do not call that a content-conflict check. Verify both file recovery and accepted business completion before treating the job as complete.

For protected-value erasure, distinguish public JSON cases from the opaque decision API, and missing references from ownership-scope failures. Verify owner authorization, a single reference's key operation, separately accepted completion, and explicit retry after restart. Keep retained ciphertext, independently protected derivatives, stored query plaintext and exported copies separate. Do not promise automatic pending-request recovery or physical deletion of file bytes from key erasure.

For command-outcome lessons, trace acceptance through stream selection, stream guards and append separately. Check empty event arrays independently: an empty result may still require an entity identity and existence checks while skipping an append-position check. Do not infer no-op behavior from a nonempty acceptance example. Keep proposed events visually distinct from recorded events. When alternative outcomes stack on phones, join each branch to its shared origin with a tree elbow and stop the rail at the last branch. A downward stem below a terminal outcome can falsely imply that another outcome follows it.

For entity and concurrency lessons, inspect which assertions actually execute in each backend fixture. A passing test name can conceal a backend-gated body. Separate event-store append contention, executor refetch and decision rerun, and an application-level race; evidence for one does not establish all three. Keep independent streams distinct in both prose and figure geometry.

For testing lessons, verify the runner's failure behavior as well as the example failure. A command may stop after unit failures and skip HTTP scenarios. Distinguish observed failures from consequences inferred for skipped checks. Capture the deliberate failure and restored success without changing the expected behavior.

For behavior changes, establish whether the affected command, event or query has been deployed before proposing an edit. Deployed definitions and implementations remain frozen. Verify `neo lock --all` and the normal `neo build` refusal against a modified locked file at the reader's CLI revision; tests and run may not invoke that check. Add a separately named command/query/event and a new feature slice for new behavior, accepting deliberate duplication rather than changing a shared helper beneath a deployed identity. Retain existing tests and add separate new-behavior checks. Preserve history and migrate callers explicitly; keeping an old entry point available preserves its old behavior too. Transport declarations are part of the command source, so a later transport guide must not edit a frozen command's TransportsOf. Add new command identities and composition instead. Distinguish predeployment experiments from changes to deployed behavior throughout subsequent guides.

Keep revisions, commands, output, review reports, and verification limits under ignored `.agents-state/`. Separate source inspection, executed behavior, and approved product intent. Public prose explains the task confidently without a source-audit sidebar. A real contradiction that prevents honest instructions is a blocker to resolve, not a disclaimer to hide in the article.

## Teach through meaningful inspection

Use [documentation voice](documentation-voice.md) for article tone and composition. Establish the subject and enough context for a direct landing, rather than beginning every page with an instruction. Use named links when reusing a prior example. For a link to another documentation page, use its navigation name as the link text, taking `sidebar.label` when present and otherwise the page title. An article heading may differ from its navigation name; use the name readers see in the sidebar so they can recognize the destination. Prefer a relevant local documentation page over an upstream source link for reader-facing navigation, even when the local page is not yet complete. Link external sources inline when they substantiate a factual claim or the reader needs the upstream artifact itself. Introduce unfamiliar mechanisms through their concrete purpose before using them to explain another mechanism.

Prefer the least technical built-in route that completes the reader's task. When the running application includes browser documentation or a suitable interface, teach that route before introducing terminal HTTP clients or other external tools. Inspect the actual interface and its controls before naming them. Command-line checks can remain internal verification evidence without becoming reader instructions. Use an external tool in the lesson only when the built-in route cannot serve its goal.

AI-assisted building is the normal path. Give the agent a bounded task and the developer something specific to inspect. When manual and agent routes are alternatives, introduce the choice before the first action so sequential readers do not perform both. Trust comes from understanding small changes and checking their behavior, not from telling readers to trust an agent. Counter orients the reader to the real starter. The mug shop remains the continuing application example elsewhere.

Make example values recognizable as examples without relying on English fluency. Choose names that state their role, and explain beside the first use whether a value is chosen freely, required literally, or returned by the application. For example, in a payload such as `{"label": "Example counter"}`, say that `Example counter` is the name chosen for this example and that another name also works. A word such as `downloads` can look like an instruction or a special system value; its familiarity to the author is not enough. Preserve exact required keys and real returned identifiers, distinguishing them from freely chosen values. Review examples for this ambiguity as well as syntax and behavior.

For source orientation, pair short, relevant excerpts with explanations of what to notice. Let readers see the declaration, condition, or calculation being discussed instead of describing several files in uninterrupted prose. Keep each excerpt beside its purpose, identify omitted context, and distinguish reading from editing. A directory map locates files; it does not replace showing the behavior inside them.

For every substantive documentation page, identify the hardest relationship or mechanism the reader must grasp and make it visible beside the explanation. Add a purpose-built figure by default: show concrete inputs, movement or transformation, intermediate state when relevant, and the resulting answer or failure. Screenshots teach recognition and code teaches syntax; neither substitutes for a data-flow or causal figure when the difficult idea is how the software works. Use the four introductory pages as the visual-teaching baseline, preserving their accepted implementation. A short operational page may omit a figure only when there is no meaningful relationship to visualize; record that reason internally rather than inserting filler. Do not meet this requirement with a decorative card, code block or table alone when the reader needs to trace a flow.

Before building, write the reader's question and the one relationship the visual must reveal in local review evidence. Apply minimal-teaching-visuals and neohaskell-visual-language. Prefer repo-native HTML/SVG/CSS with selectable labels. Use a static diagram for dependencies or stable comparisons; use a short animation when sequence, data movement or state transitions supply the missing understanding. Interaction earns its place when the reader needs to compare or inspect states, not merely to advance through the article. Preserve events versus derived answers, frozen identities, exact failure conditions, and the difference between illustration and executed evidence. Show how an incompatible contract change can break a caller or replay without claiming every edit necessarily fails. Keep essential meaning visible on phones and with reduced motion, and give animations a useful static fallback. Complete the fresh learning-example-review visual correction loop before delivery.

Prefer an authentic screenshot when recognizing a real interface is the point, and a diagram when relationships would otherwise be hard to see. Explain what to notice in the main prose; omit decorative captions, figure identity labels and repeated instructions. Keep essential instructions selectable. A visual supports the page's task rather than expanding its technical scope.

Place each figure immediately beside the idea it explains. When a dependency or risk motivates the whole page, show it near the opening before implementation details. Design a visible focal point and reading path: use connected shapes, meaningful symbols, position and visual hierarchy to reveal the mechanism. Do not substitute a grid of text cards for a diagram. Use danger color and a broken connection or other non-color cue for an actual failure; keep command/event/query semantic colors intact. Remove repeated labels and secondary text that compete with the main relationship. Review the figure at a glance before reading its prose.

Preserve the convictions in `PRODUCT.md`: developer judgment, agency, enjoyment, and coherent built-in choices. Each paragraph needs a substantive job, but not every paragraph needs a new mechanism. For conceptual arguments, connect examples to the claim rather than listing capabilities. Comparisons with other approaches are an internal test of the argument, not required public concessions. Native previous/next links own onward navigation; end when the subject is resolved.

## Review and deliver

Request independent technical and pedagogical review when authorized, as required by the page effort. Give reviewers the page goal, accepted baseline, source revisions, and evidence, with a report-only write boundary. The pedagogical reviewer should challenge the argument as a fresh reader, not only check spelling or vocabulary. Ask where the reader must guess, what they can inspect, whether the example supports the intended conclusion, and whether the rendered reading rhythm fits the approved pages. Review connected explanation against the voice reference too: repeated task announcements, a chain of imperative sections, and generic benefit claims need paragraph-level repairs, not just heading substitutions.

For changed teaching examples, combine that fresh review with the installed `learning-example-review` visual loop where practical. Include desktop and phone captures at normal zoom, computed text sizes, and an accepted neighboring section. Judge the raw captures before the implementation. Apply material findings, then verify corrections against the same evidence conditions. Distinguish reviewer approval from owner acceptance and from measured reader comprehension.

Before completion, inspect the rendered article and navigation, remove redundant auxiliary text, and run the repository's applicable checks. A passing build does not establish that instructions work or that an explanation teaches. Complete only when the page's stated result, source claims, review findings, and rendered content have each been checked, or record the exact blocker in its ticket.

For incoming identity lessons, compare verified, invalid and absent bearer tokens as distinct paths. An anonymous request still reaches access policy; an invalid token stops before the command. Do not place failure downstream of a node labeled verified identity or connect a terminal rejection to a later command. Check audience configuration separately from signature rejection, and distinguish controlled injected auth fixtures from public OIDC discovery.

For command authorization, distinguish the claims-only gate from entity ownership inside the decision. Show the stored entity as a decision input, terminal denials as separate branches, and trusted gate bypass without implying authenticated ownership. Establish an owner-bearing entity explicitly when the preceding tutorial only modeled shop stock.

For query visibility, trace the claims gate, stored-row policy, collection filtering and by-ID denial separately. Verify pagination counts after visibility and client filters. Do not carry command trusted-bypass behavior into query handlers. Check generated query declaration names against the current public API. On phones, keep policy identifiers intact in tables and wrap agent prompts at natural task boundaries.

For external OAuth connections, separate inbound identity, temporary callback transactions and provider credentials. Trace success-command dispatch through its queue before claiming business completion. Check provider-error callbacks independently from token-exchange failure; an onFailure mapping need not cover every rejection. Verify each URL field's validation separately, and distinguish local token deletion, its reported errors and provider-side revocation. A persistent secret store does not establish durable pending transactions.

For deployment lessons, distinguish a native executable on its build machine from a portable release artifact. Trace configuration fields into the listener rather than assuming an environment variable changes its bind address. Verify retained history with an actual process replacement and a decision against recovered state. Keep deployment history and empty-history test fixtures in separate directories, with fresh scenario identities. Show retained services outside the process boundary; on phones, omit an unrelated ingress path if stacking would imply requests flow through storage.

For operational readiness, verify implementation precedence against aggregate state comments, and distinguish startup replay status from failures in live query maintenance. A ready probe need not detect a logged live updater failure. Trace one real rejected command through its generated request identifier and structured result fields; do not assume the response exposes that identifier. Separate business refusal, reported storage failure and downstream provider failure, including adapter-specific persistence warning behavior.

For declaration hierarchies, distinguish containment from causal connections. Keep each modeled event visibly associated with its command slice, and trace connector endpoints again after responsive reflow. A feature tree should not imply that source order schedules its slices.

For history/state lessons, distinguish repeatable reconstruction with an unchanged reducer from a migration to a changed interpretation. A snapshot contains state already computed under an interpretation; replaying its suffix does not recompute that prefix. Check the CLI's actual lock discovery before claiming automatic enforcement: an entity reducer outside discovered command/event/query paths still requires preserving deployed behavior, even when the normal build passes.

For projection lessons, trace the actual updater input before illustrating an event fold. A triggering event can cause a fetch of the entity's current complete state, including later changes. Distinguish this from calculating an as-of-event state. For multiple entity contributors, explain the shared row identity, per-source replacement and any needed fanout; atomic row updates do not create a transaction across their command streams. Keep saved rows separate from durable replay progress.

For decision/effect lessons, distinguish constructing a Decision from interpreting it as a Task. RequestContext is caller input; DecisionContext supplies interpreter capabilities. UUID generation and protected-value cryptography/key lookup mean interpretation is not effect-free. Control generated values for exact assertions, and compare protected-value semantics rather than promising repeatable ciphertext. Keep acceptance, successful event persistence, provider success and a receiving command's acceptance as separate outcomes.

For cross-entity workflows, show the originating event in its own history and the receiving command's separate decision and history. Provider success can precede a refused receiving command, so label missing local events separately from missing external effects. Draw failure outcomes as terminal branches rather than intermediate steps on the success path. Do not infer automatic recovery or exactly-once effects from event-driven dispatch; pending work, provider reconciliation and duplicate handling need explicit application behavior.

For identity concepts, carry one verified caller through operation permission, stored ownership and business acceptance. Establish an owner-bearing entity when the stock tutorial has none. Keep query row visibility separate from command decisions, and distinguish an absent token reaching policy from an invalid token stopping at authentication. A requested comparison table may complement a causal figure; preserve its bounded cases rather than removing an explicit teaching requirement as duplication.

For reusable integration lessons, keep protocol modules outside application-domain directories and inspect imports as well as types. Show application-owned input and result mappings explicitly. Distinguish the supplied Integration.ToAction configuration route from Service.Integration.Adapter's associated Response/runReal/runFake contract and their different error types. A schema instance supplies structure, not codecs or fake response generation. Exercise the generic wrapper independently against a controlled local service, then keep command dispatch and business acceptance as separate checks. TypedInbound output restrictions do not convert a legacy Inbound into a typed worker or prove acceptance. HTTP onSuccess can receive a non-success status; response bodies are already Json.Value, so distinguish protocol decoding from status handling and expose safe application errors.

For resource-lifecycle lessons, inspect Application's registration factory separately from the lower-level integration tuple builder. Keep per-stream outbound state distinct from durable entity state, and raw lifecycle events distinct from typed handler inputs. Verify actual cleanup notifications rather than treating shutdown return as proof: dispatcher stopping can be asynchronous. Inbound resources belong inside run, with cancellation-safe acquisition, release and explicit joining. A pending lifecycle test is not executed coverage; use controlled resources when maintained tests leave that path untested. Keep resource release, command acceptance and business completion separate.
