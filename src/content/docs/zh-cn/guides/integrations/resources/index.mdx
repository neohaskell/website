## 客户端属于工作器的生命周期

无状态出站处理器为每个事件构造要执行的工作，不会在多次调用之间保留客户端。当现有集成已经管理所需资源时，请使用这条路径。如果你自己的集成需要可供多个事件复用的昂贵客户端、连接或解释器，那么加入生命周期钩子会很有用。

[`Integration.Lifecycle.OutboundConfig`](https://github.com/neohaskell/NeoHaskell/blob/414602b9510a92dfac647bc68d6afadfb594502c/core/service/Integration/Lifecycle.hs)描述了第二种路径。分发器会为一个实体流创建工作器，并将初始化后的状态交给每个事件处理器。同一流的事件会依次运行。不同流可以有各自的工作器，因此这里创建的资源不是整个应用共用的单例。

## 三个钩子，一个资源负责人

配置有三个字段。在这些签名中，`state` 是初始化返回的资源值，例如配送客户端：

```haskell
initialize :: StreamId -> Task Text state
processEvent ::
  state ->
  Event Json.Value ->
  Task Text (Array Integration.CommandPayload)
cleanup :: state -> Task Text Unit
```

`Task error value` 描述一种可能以错误失败，也可能以值完成的工作。这里的错误是 `Text`；初始化返回 `state`，事件处理返回命令载荷，清理则返回 `Unit`，表示没有有用的结果值。构造 Task 不会运行它。[任务与副作用](/reference/core/tasks/)会单独介绍执行方式和业务决策接受命令之间的区别。

初始化会收到流标识。当提供方资源需要限定到某个实体时，可以使用它。初始化成功后，分发器会保留返回的资源，并将其传给 `processEvent` 和 `cleanup`。资源状态是普通的运行时状态；这些钩子不会让状态在进程重启后仍然持久化。

传给 `processEvent` 的事件是原始的 `Event Json.Value`。请解码集成能够处理的事件，并将它们映射到协议输入。使用 `Integration.makeCommandPayload` 编码命令，并返回供应用分发的命令载荷。应用的映射应留在通用客户端模块之外。这种较底层的生命周期记录与前一篇指南中的带类型出站处理器是两条不同的路径；它不会自动提供带类型的事件载荷，也不会还原实体状态。

清理会释放初始化返回的资源。请关闭客户端，并停止它所拥有的任何辅助工作。清理应简短，并且能够安全地重试。如果初始化打开连接后、返回连接之前便失败，它必须自行释放该连接，因为分发器没有成功收到可供清理的状态。依次获取多个资源时也要同样处理。

## 空闲工作器的移除与分发器关闭

分发器会定期检查空闲工作器。移除工作器会结束该工作器的资源生命周期；后续事件会创建另一个工作器，并再次调用初始化。因此，对于同一实体，初始化必须能够承受多次生命周期。它应打开客户端，而不是重复执行预订配送这项业务操作。

使用 `Application.withOutboundLifecycle @() @MugOrderEntity (\_ -> config)` 注册这条路径，其中 `config` 是你的 `Lifecycle.OutboundConfig` 值。第一个类型参数指定 `()` 类型，工厂会忽略该配置值。如果设置由应用启动时提供，请改用应用配置类型，并根据配置值构造客户端配置。只需在应用组合处加入所需的导入和注册，不要替换整套设置。保留已部署的命令、事件和查询定义。如果现有的已部署接收端不允许 `InternalTransport`，钩子可以返回一个新的接收命令，详情见[安全地添加功能](/tutorial/change-safely/)。

工作器正常停止时会调用清理。分发器关闭会启动停止流程，但仅凭其返回不能证明所有资源都已释放。强制取消、进程终止和正常完成的优雅停止也有所不同。不要把清理当作记录配送待处理或已完成状态的唯一依据。

事件处理失败后可能会由分发器重试，因此提供方操作需要明确的重复处理策略。清理失败无法撤销已接受的马克杯订单，也无法取消提供方已完成的预订。请在应用状态中保留持久的操作标识和待处理状态；如果提供方支持幂等键，请使用稳定的幂等键。若提供方操作结果不确定，应先核实并协调该结果，再将重试视为新的预订。

## 入站工作器负责获取资源

入站集成的方向相反：它等待提供方输入，然后发出应用命令。其资源生命周期应放在 `run` 函数中管理。入站配置没有与 `initialize`、`processEvent` 和 `cleanup` 对应的记录。

`Integration.InboundConfig` 和 `Integration.TypedInboundConfig` 都会向 `run` 提供一个发出函数。带类型的版本限制了它可以发出的命令和目标实体。这两种配置都不会自动管理提供方连接。工作器应获取输入连接、运行读取循环，并在循环结束或失败时释放连接。

对于拥有已获取资源的工作，请使用 `Task.finally release work`。第一个参数是清理 Task。这会保护读取循环在退出时执行清理，包括取消时；获取资源本身也必须处理部分失败，以及将资源安全交给受保护工作的过程。在生产环境中，需要使用可安全应对取消的获取和释放模式，防止刚获取句柄就遭遇取消，而清理尚未就位。

入站工作器返回集成错误时，应用会加入退避后重启它。每次尝试都必须先释放自己获取的资源，下一次尝试才能打开替代资源。正常完成的运行则会结束，不会重启。应用关闭时，运行时会取消入站任务，并使用 `AsyncTask.waitCatch` 等待它们结束。等待会持续到工作器及其清理均已退出。如果清理永远阻塞，等待也可能一直阻塞。

## 资源释放与配送完成

监听器正在等待下一条通知，表示工作正常进行中。监听器发出了 `RecordShipmentBooking`，表示它已提交一条命令。配送实体的接收决策接受并记录预订后，才有了业务结果。这些情况回答的是不同的问题。

请让你的智能体使用受控资源，分别测试这些边界。对于出站工作，应测试一个流中的初始化、复用、空闲清理和重新初始化，以及不同流之间的隔离。还要覆盖处理失败、部分获取失败和关闭。对于入站工作，应统计正常返回、失败、重启和取消时的获取与释放次数，然后等待工作器结束，并检查之后是否还会收到通知。还应单独检查最终配送状态，不要把它与资源计数混为一谈。

套接字已关闭，只能证明资源已释放。它不能证明最后一条通知已被接受、提供方操作已被撤销，也不能证明重启后待处理工作会继续。这些结果需要各自的应用命令、保留事实和恢复策略。
