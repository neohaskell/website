Առաքման մատակարարն ընդունում է ամրագրման հարցում և վերադարձնում ամրագրման արդյունք։ Պետք չէ, որ նա իմանա, թե գավաթների խանութն ինչպես է գրանցում պատվերը, որ էությունն է պատասխանատու առաքման համար կամ երբ առաքման որոշումը պետք է մերժի փոփոխությունը։ Այդ ընտրությունները պատկանում են հավելվածին։

[Աշխատանքային հոսքեր էությունների միջև](/concepts/event-driven-workflows/) էջում ընդունված պատվերը հանգեցնում է առանձին առաքման էության հետ աշխատանքին։ Այստեղ մատակարարի հետ հաղորդակցվող մասը տեղափոխում ենք մի մոդուլ, որը կարող է վերօգտագործել մեկ այլ հավելված։ Սա արդեն գործող հավելվածի համար նախատեսված առաջադեմ ուղեցույց է։ Դուք պետք է կարողանաք ճանաչել հրամանի, իրադարձության և Feature հայտարարությունները։ Օրինակներում ինտեգրմանը հատուկ պայմանագրերը ներկայացվում են հենց տեղում։

Վերօգտագործելի մոդուլը պատասխանատու է մատակարարի արձանագրության համար։ Հավելվածն է պատասխանատու երկու համապատասխանեցումների համար՝ իրադարձությունից դեպի մատակարարի մուտք և մատակարարի արդյունքից դեպի նոր հրաման։ Հաջող ամրագրումը դեռ պետք է անցնի ստացող հրամանի որոշումը, որպեսզի հավելվածը գրանցի առաքման փաստը։

## Պայմանագիր խանութից դուրս

Ընդհանուր կոդը տեղադրեք `src/Shipping/Booking.hs`-ում՝ `src/MyShop`-ից դուրս։ Այն կարող է ներմուծել NeoHaskell-ի մոդուլներն ու մատակարարի օժանդակ գրադարանները, բայց չպետք է ներմուծի խանութի էությունները, իրադարձությունները կամ հրամանները։ Հակառակ դեպքում հաջորդ հավելվածը ստիպված կլինի կախված լինել գավաթների խանութից՝ առաքում ամրագրելու համար։

Որպես մեկնարկային ֆայլ օգտագործեք [Shipping.Booking ամբողջական մոդուլը](/examples/shipping-booking.hs), իսկ հավելվածից ներմուծեք այն որպես `Shipping.Booking qualified as Shipping`։ Դրա HTTP կարգավորման մեջ նույնականացում չի պահանջվում, ուստի այն կարող է աշխատել վերահսկվող տեղային մատակարարի հետ։ Տեղակայված մատակարարի համար կարգավորեք դրա պահանջած նույնականացումը։

Հետևյալ հատվածները նկարագրում են տրամադրված `Integration.Http` ինտեգրման շուրջ փոքր փաթեթավորիչ։ Դրանք ցույց են տալիս պայմանագրերն ու համապատասխանեցման կետերը, ոչ թե ամբողջական հավելվածը։ `Request`-ը և `Booking`-ը `Shipping.Booking`-ում սահմանվող տիպեր են՝

```haskell
data Request = Request {
  reference :: Text,
  quantity :: Int
} deriving (Generic)

instance Json.ToJSON Request

data Booking = Booking {
  status :: Text
} deriving (Generic)

instance Json.FromJSON Booking
```

reference դաշտը նույնացնում է մատակարարի այս գործողությունը, իսկ quantity դաշտը ցույց է տալիս, թե քանի տարր է այն ներառում։ Դաշտերից ոչ մեկը չի կրում խանութի իրադարձության կամ էության տիպը։ Իրական մատակարարի պայմանագրում այստեղ ավելացրեք առաքման վայրը և պահանջվող մյուս դաշտերը, այլ ոչ թե ամբողջ տիրույթային իրադարձությունը փոխանցեք որպես JSON։

`Generic`-ն աջակցում է այստեղ օգտագործվող ընդհանուր կոդավորման ու վերծանման օրինակներին։ `Json.ToJSON`-ը կոդավորում է հարցումը, իսկ `Json.FromJSON`-ը վերծանում է պատասխանը։ Դրանք տարբեր պարտականություններ են։ `Schema.ToSchema` օրինակը տալիս է կառուցվածքային նկարագրություն։ Այն ինքնուրույն չի վերծանում պատասխանը, չի վավերացնում մատակարարի բոլոր կանոնները և չի ստեղծում իրատեսական թեստային պատասխաններ։

## HTTP փաթեթավորիչն ու դրա արդյունքը

Փաթեթավորիչն ընդունում է մատակարարի URL-ը, հարցումը և այն կանչող ֆունկցիան՝

```haskell
request ::
  Text ->
  Request ->
  (Result Text Booking -> command) ->
  Http.Request command
```

Հետադարձ կանչը կարող է ստանալ կամ սխալի հաղորդագրություն, կամ վերծանված ամրագրում, և վերադարձնում է հրաման։ `command` տիպի փոփոխականը թույլ է տալիս յուրաքանչյուր հավելվածի ընտրել իր հրամանը՝ առանց առաքման մոդուլից այն ներմուծելու։ URL-ը պահեք կարգավորման մեջ։ Loopback հասցեն հարմար է վերահսկվող տեղային մատակարարի համար, իսկ տեղակայված մատակարարին պետք են իր իրական վերջնակետն ու նույնականացումը։

Փաթեթավորիչի ներսում կառուցեք `Http.Request`՝ նշելով `method = Http.POST`, `body = Http.json input`, կարգավորված URL-ը և նույնականացման, ժամանակի սահմանափակման ու կրկնափորձի բացահայտ կարգավորումները։ Պատասխանի հետադարձ կանչը նախ պետք է ստուգի HTTP կարգավիճակը, հետո միայն վերծանի մարմինը։ Տրամադրված `onSuccess` անունը նշանակում է, որ պատասխան է եկել։ 503 պատասխանը միևնույն է պետք է վերածել ձախողված ամրագրման արդյունքի։ Ընդունված պատասխանը վերծանեք `Json.decode @Booking response.body`-ով։ Անվավեր մարմինը հորինված ամրագրման փոխարեն պետք է դառնա սխալի արդյունք։

Հետո հետադարձ կանչի երկու դաշտերն էլ դիմում են հավելվածի ֆունկցիային՝

```haskell
onSuccess = \response -> toCommand (decodeBooking response),
onError = Just (\_ ->
  toCommand (Err "Shipping provider could not be reached"))
```

Այստեղ `decodeBooking`-ը մեր կարգավիճակը ստուգող վերծանիչն է, ոչ թե ֆրեյմվորքի ֆունկցիա։ Մատակարարի ախտորոշիչ տեղեկությունները պահեք կանչողներին ցուցադրվող հաղորդագրություններից առանձին և մի վերադարձրեք հավաստագրերը կամ զգայուն պատասխանի հում մարմինը։ Կրկնափորձի վարքն ընտրեք մտածված և, եթե մատակարարի արձանագրությունն աջակցում է, ուղարկեք կայուն իդեմպոտենտության բանալի։ HTTP կանչի կրկնափորձն ու հավելվածի դիսպետչերի կրկնափորձը տարբեր գործողություններ են. դրանցից ոչ մեկը չի երաշխավորում մեկանգամյա կատարում։

## Համապատասխանեցումները մնում են MyShop-ում

Խանութի իրադարձության մշակիչը ընդունված պատվերից կառուցում է `Shipping.Request`-ը և տրամադրում արդյունքի համապատասխանեցումը։ Այս հարմարեցված հատվածում `event`-ը նոր պատվերի տվյալներն են, `request`-ը մատակարարին ուղարկվող մուտքն է, իսկ հետադարձ կանչը պահպանում է հավելվածի ընտրած առաքման նույնացուցիչը՝

```haskell
Shipping.request providerUrl request \result ->
  case result of
    Ok booking -> RecordShipmentBooking {
      entityId = event.shipmentId,
      status = booking.status
    }
    Err _ -> RecordShipmentBooking {
      entityId = event.shipmentId,
      status = "provider-failed"
    }
```

Պատկերավոր հրամանի այս դաշտերը խանութին են պատկանում։ Մատակարարի արդյունքը չի որոշում, թե խանութն ինչ կարող է գրանցել։ Օրինակ՝ առաքման որոշումը կարող է մերժել անհայտ կարգավիճակը, նույնիսկ եթե մատակարարն արդեն ամրագրել է առաքումը։ Այդ մերժումը չի վերացնում մատակարարի գործողությունը կամ սկզբնական պատվերի իրադարձությունը։

Կարգավորված հարցումը փաթեթավորեք `Integration.outbound`-ով և դրա գործողությունը հավաքեք `Integration.batch`-ով՝ հավելվածի ելքային մշակիչում։ Մշակիչը գրանցեք իր Feature-ում։ Որպեսզի ինտեգրման դիսպետչերը հասնի ստացող հրամանին, այդ հրամանը պետք է թույլատրի `InternalTransport`-ը, իսկ դրա մշակիչը պետք է գրանցված լինի։ Եթե գործող համակարգում արդեն տեղակայված ստացողը չի թույլատրում այդ փոխադրումը, սառեցված հայտարարությունը փոխելու փոխարեն ավելացրեք հրամանի նոր նույնացուցիչ և սլայս։ Պահպանեք նաև տեղակայված իրադարձություններն ու հարցումները, ինչպես բացատրված է [Անվտանգ ավելացրեք առանձնահատկություն](/tutorial/change-safely/) էջում։

## Առաջադրանքներ ադապտերի ներսում

Վերօգտագործելի ինտեգրման հեղինակը պետք է հասկանա նաև կարգավորման գրառումներից այն կողմ կատարվող աշխատանքը։ `Task error value`-ը նկարագրում է աշխատանք, որը կարող է ձախողվել `error`-ով կամ ավարտվել `value`-ով։ Task կազմելը չի գործարկում դրա HTTP կանչը։ `do` բլոկում `<-`-ը հաջորդ քայլին փոխանցում է հաջող արժեքը։ Ձախողման դեպքում հետագա քայլերը չեն կատարվում, եթե կոդը դա չի մշակում։ Ինտեգրման գործողությունները կատարում է գործարկման միջավայրը։ [Առաջադրանքներ և կողմնակի ազդեցություններ](/reference/core/tasks/) էջը այս պայմանագիրը բացատրում է բիզնես որոշման ընդունումից կամ մերժումից առանձին։

Տրամադրված HTTP փաթեթավորիչը օգտագործում է `Integration.ToAction`՝ իր կարգավորումը գործողության վերածելու համար։ Ավելի ցածր մակարդակի տիպավորված հարցման ադապտերն ունի այլ պայմանագիր՝ [`Service.Integration.Adapter`](https://github.com/neohaskell/NeoHaskell/blob/414602b9510a92dfac647bc68d6afadfb594502c/core/service/Service/Integration/Adapter.hs)-ում։ `Integration request` օրինակը հարցումը կապում է `Response request`-ի հետ և իրականացնում է `runReal`-ն ու `runFake`-ը։ Յուրաքանչյուր գործողություն վերադարձնում է ադապտերի `IntegrationError` տիպով Task։ Ադապտերի սխալի այս տիպը տարբերվում է `Integration` ֆասադի տրամադրած սխալի տիպից։

Նման ադապտերը փորձարկելիս հստակ իրականացրեք կանխորոշված կեղծ տարբերակը։ Օրինակ՝ մի ընտրված հարցման համար վերադարձեք հաստատուն ամրագրման պատասխան, իսկ մեկ ուրիշի համար՝ տիպավորված ձախողում։ Սխեման `runFake`-ի իրականացում չէ։ Ադապտերի կեղծ տարբերակի ուղղակի թեստերն էլ չեն ապացուցում, որ գործող հավելվածը յուրաքանչյուր մատակարարի հարցումն ուղղում է այդ տարբերակին։

## Մուտքային աշխատանքն էլ ունի սեփականության նույն սահմանը

Մուտքային ինտեգրման դեպքում վերօգտագործելի կոդն է պատասխանատու արտաքին մուտքը կարդալու և վերծանելու համար։ Հավելվածն է վերծանված ծանուցումը համապատասխանեցնում իր հրամանին։ Այդ համապատասխանեցումը պահեք արձանագրությունը կարդացող կոդից դուրս, ինչպես ելքային փաթեթավորիչում խանութի արդյունքի համապատասխանեցումը պահվում է HTTP մշակման կոդից դուրս։

Տիպավորված մուտքային API-ն թույլատրելի ելքերը ներկայացնում է հրամանների և էությունների զույգերի ցանկով։ Օրինակ՝ `Integration.TypedInbound '[ '(RecordShipmentBooking, ShipmentEntity)]` վերադարձնող հավելվածի աշխատողը հայտարարում է և՛ այն հրամանը, որը կարող է արձակել, և՛ դրա թիրախ էությունը։ `Integration.TypedInboundConfig`-ը աշխատողին տրամադրում է այդ ցանկով սահմանափակված արձակման ֆունկցիա։ Հրամանը պետք է ունենա իր անվան և JSON կոդավորման օրինակները, իսկ էությունը պետք է համապատասխանի հայտարարված զույգին։ Այս ստուգումները սահմանափակում են ելքերը, բայց չեն ապացուցում, որ ստացող հրամանը կընդունի յուրաքանչյուր ծանուցում։

`Integration.asInbound`-ը տիպավորված աշխատողը փոխակերպում է `Inbound` գրանցման հին ձևի արժեքի։ Տրամադրված `Timer.every`-ն արդեն վերադարձնում է գրանցման հին ձևի `Inbound`։ Այն տիպավորված աշխատող կառուցող միջոց չէ։ Մոդելի վրա հիմնված տիպավորված հայտարարումն օգտագործելիս ինտեգրման հեղինակը պետք է ուղղակիորեն տրամադրի տիպավորված աշխատողը և չխոստանա, թե հին ձևի աշխատողը կարելի է հակառակ ուղղությամբ փոխակերպել։ Ռեսուրսի ձեռքբերման, չեղարկման և ազատման պատասխանատվությունը հստակ սահմանեք, ինչպես բացատրված է [Կառավարեք ինտեգրման ռեսուրսները](../resources/) էջում։

## Թեստեր՝ այլ հավելվածներում օգտագործելու համար

Վերօգտագործելի մոդուլը փորձարկեք առանց `MyShop` ներմուծելու։ Ստուգեք հարցման կոդավորումը, ընդունված պատասխանի վերծանումը, անհաջող կարգավիճակը, սխալ ձևավորված պատասխանը և կապի ձախողումը։ Հետո առանձին փորձարկեք հավելվածի համապատասխանեցումները, այդ թվում՝ ստացող որոշման կողմից մերժված արդյունքը։ Վերահսկվող տեղային HTTP ծառայությունը թույլ է տալիս տրամադրված իրական կլիենտով փորձարկել այս դեպքերը՝ առանց հավաստագրերի կամ արտաքին ազդեցությունների։ Ստուգեք ստացված առաքման վիճակը և պատվերի ընդունումը. դրանք առանձին արդյունքներ են։

Վերօգտագործելի կոդն ու դրա թեստերը միասին ներառեք [NeoHaskell monorepo](https://github.com/neohaskell/NeoHaskell)-ում ներդրում անելիս։ Ներառեք արձանագրության պայմանագիրը, նույնականացման պահանջները և փորձարկված ձախողման դեպքերը, որպեսզի մեկ այլ հավելված կարողանա կարգավորել ինտեգրումը՝ առանց խանութի տիրույթը որդեգրելու։ Neo packages-ը ապագա տարածման ուղղություն է, իսկ այսօր ներդրումներ կատարելու ուղին monorepo-ն է։
