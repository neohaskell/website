Ընդունված գավաթի պատվերը կարող է առաքման հարցում առաջացնել։ Մատակարարը կարող է ամրագրել առաքումը, բայց խանութին դեռ պետք է արդյունքը գրանցող հրաման։ Ինտեգրումը կապում է այս քայլերը՝ առաքման կանչը պատվերի որոշման մեջ չտեղափոխելով։

Այս տեղեկատուն հիմնվում է [Իրադարձությունների մոդելներ և առանձնահատկություններ](../) և [Առաջադրանքներ և կողմնակի ազդեցություններ](../../core/tasks/) էջերի վրա։ Մատակարարի ամբողջական փաթեթավորիչի համար օգտագործեք [Ստեղծեք վերօգտագործելի ինտեգրում](/guides/integrations/create-reusable/) ուղեցույցը։ Այստեղի պայմանագրերն օգնում են ստուգել, թե գործակալն ինչ աշխատանք է կարգավորել, ով է պատասխանատու համապատասխանեցումների համար, և իրականում ինչ է ապացուցում ավարտված աշխատողը։

## Գրանցված իրադարձությունից դեպի մեկ այլ որոշում <a id="outbound" />

Հավելվածը գրանցված պատվերի իրադարձությունը համապատասխանեցնում է մատակարարին ուղղված հարցմանը։ Վերօգտագործելի առաքման մոդուլը պատասխանատու է արձանագրության ու վերծանման համար։ Այն գտնվում է `src/MyShop`-ից դուրս և չի ներմուծում խանութի հրամաններն ու էությունները։ Հավելվածն է ամրագրման արդյունքը համապատասխանեցնում առաքումը գրանցող հրամանին։

<IntegrationContract />

Մատակարարի վերադարձած պատասխանը ինքնին չի նշանակում, որ ամրագրումը հաջողվել է։ Հաջող ամրագրումն ինքնին չի նշանակում, որ առաքման հրամանն ընդունվել է։ Ստացող հրամանն իր որոշումն է կիրառում, իսկ առաքման հարցման վիճակը թարմանում է առանձին։ Հրամանի մերժումը չի վերացնում սկզբնական պատվերը կամ մատակարարի գործողությունը։

## ToAction-ով կարգավորված գործողություններ <a id="actions" />

`Integration` ֆասադը տրամադրում է կազմաձևումից գործողություն տանող ուղին, որն օգտագործում է տրամադրված `Integration.Http` մոդուլը՝

```haskell
class ToAction config where
  toAction :: config -> Action

outbound :: ToAction config => config -> Action
batch :: Array Action -> Outbound
```

`outbound`-ը մեկ կարգավորման արժեքը վերածում է գործողության։ `batch`-ը հավաքում է այդ գործողությունները `Outbound` արժեքի մեջ, որը վերադարձնում է հավելվածի մշակիչը։ `Integration.none`-ը իրադարձության համար ոչ մի գործողություն չի վերադարձնում։ Այս ֆունկցիաները նկարագրում են աշխատանքը։ Դիսպետչերը կատարում է այն, երբ իրադարձությունը հասնում է մշակիչին։

Ինտեգրման հեղինակը կարող է գործողություն կառուցել անմիջապես այս սահմանին՝

```haskell
action ::
  (ActionContext -> Task IntegrationError (Maybe CommandPayload)) ->
  Action
```

`ActionContext`-ը տրամադրում է գործարկման միջավայրի ծառայություններ, այդ թվում՝ գրանցված ելքային դիսպետչերը։ Գործողությունը կարող է վերադարձնել ստացող հրաման չլինելու նշում կամ կոդավորված հրամանի տվյալներ։ `Integration.emitCommand command`-ը կազմում է հաջող Task, որը վերադարձնում է այդ տվյալները։ `Integration.noCommand`-ը ոչինչ չի վերադարձնում։ Այս օգնականներից ոչ մեկը չի ապացուցում, որ ստացող որոշումն ընդունել է հրամանը։

`Integration.makeCommandPayload`-ը մաքուր կոդավորման օգնականն է։ Դրա համար անհրաժեշտ են `Json.ToJSON command` և հայտնի `NameOf command`։ Դիսպետչերին անհրաժեշտ է նաև գրանցված ստացող, որը թույլատրում է `InternalTransport`-ը։ Եթե գործող համակարգում արդեն տեղակայված հրամանը չունի այդ թույլտվությունը, սառեցված հայտարարությունը փոխելու փոխարեն ավելացրեք հրամանի նոր նույնացուցիչ։ Այդ անցումը բացատրված է [Անվտանգ ավելացրեք առանձնահատկություն](/tutorial/change-safely/) էջում։

HTTP կարգավորման `onSuccess` հետադարձ կանչը նշանակում է, որ պատասխան է եկել։ Հաջողության հրաման կազմելուց առաջ հավելվածը կամ փաթեթավորիչը պետք է ստուգի կարգավիճակը և վերծանի մարմինը։ Արդյունքի համապատասխանեցումը ստուգելիս տարանջատեք HTTP-ի կրկնափորձերը, դիսպետչերի կրկնափորձերը և ստացող հրամանի մերժումը։

## Գրանցված հարցման ադապտերներ <a id="adapters" />

[`Service.Integration.Adapter`](https://github.com/neohaskell/NeoHaskell/blob/414602b9510a92dfac647bc68d6afadfb594502c/core/service/Service/Integration/Adapter.hs)-ը մեկ այլ ուղի է սահմանում։ Ներմուծեք այն որակավորված անունով, որպեսզի դրա `Integration` դասը տարբեր լինի ֆասադի մոդուլից՝

```haskell
import Service.Integration.Adapter qualified as Adapter
```

`Adapter.Integration request` օրինակը ընտրում է `Adapter.Response request`-ը և իրականացնում հետևյալ մեթոդները՝

```haskell
runReal :: request -> Task IntegrationError (Response request)
runFake :: request -> Task IntegrationError (Response request)
```

Այստեղ `IntegrationError`-ը պատկանում է `Service.Integration.IntegrationError`-ին, ոչ թե ֆասադին։ Ադապտերի դասը չունի JSON կոդավորման կամ սխեմայի համար վերադաս դասի սահմանափակում։ Յուրաքանչյուր իրականացում ինքն է պատասխանատու իր արձանագրության կոդավորման, վերծանման և վավերացման համար։ [JSON և սխեմաներ](../../core/json/) էջում այդ պարտականությունները տարբերակվում են կառուցվածքային նկարագրությունից և ձեռքով կազմված թեստային օրինակներից։

Գրանցեք հարցման տիպը հավելվածի կապակցման կոդում՝

```haskell
Application.new
  |> Application.withIntegration @ShippingRequest
```

`ShippingRequest`-ը ներկայացնում է ձեր ադապտերի հարցման տիպը։ Գրանցման համար պահանջվում են ադապտերի օրինակը, հարցման և պատասխանի գործարկման միջավայրի տիպի մասին տեղեկությունները, ինչպես նաև `TypeName.Inspectable request`-ը։ Հավելվածի մեկնարկին այն դիսպետչերի գրանցամատյանում գրառում է ավելացնում։ Այն չի գրանցում իրադարձության մշակիչ, պատվերը չի համապատասխանեցնում այդ հարցմանը և ստացող հրաման չի սահմանում։

`Service.Integration.ShimEmit.emit`-ը ստանում է այդ գրանցամատյանը, հետո հարցումը, և վերադարձնում է `Task IntegrationError (Response request)`։ Գրանցման բացակայության դեպքում վերադարձվում է `PermanentFailure`։ Այն լուռ կերպով իրական մատակարարին չի կանչում։ Գործողության համատեքստը հավելվածի գրանցամատյանը հասանելի է դարձնում գործողության իրականացմանը։

### Ընտրությունը կատարվում է գրանցված ուղու շրջանակում <a id="selection" />

Ադապտերի դիսպետչերը կարող է `Selection`-ից կապել `runReal`-ը կամ `runFake`-ը։ Հավելվածի մեկնարկի կոդն է վերլուծում ինտեգրման ընտրությունը և կազմում այդ ֆունկցիաները։ Դրանից չի հետևում, որ `ToAction`-ի բոլոր իրականացումներն օգտագործում են գրանցամատյանը։ Մասնավորապես, տրամադրված HTTP կարգավորումն ունի գործողության իր իրականացումը։ Ադապտերի գրանցումը չի փոխարինում այդ կլիենտի կանչերը։

Կեղծ իրականացումը բացահայտ սահմանեք և ուղղակիորեն փորձարկեք ընտրված պատասխաններն ու ձախողումները։ Սխեման `runFake`-ը չի իրականացնում, իսկ կեղծ տարբերակի հաջող ուղղակի թեստը չի ապացուցում, որ գործող հավելվածն այն ընտրել է։ Մատակարարի վարքը ստուգելու համար վերահսկվող տեղային ծառայությունը կարող է իրական HTTP կլիենտը գործարկել առանց արտաքին հավաստագրերի։ [Ստեղծեք վերօգտագործելի ինտեգրում](/guides/integrations/create-reusable/) էջը բացատրում է թեստավորման այս սահմանը։

## Տիպավորված մուտքային հրամաններ <a id="inbound" />

Մուտքային աշխատողը կարդում է արտաքին մուտքը և ներմուծում հրամաններ։ Դրա վերօգտագործելի մասը պատասխանատու է կարդալու և վերծանելու համար, իսկ հավելվածը՝ ծանուցումը հրամանին համապատասխանեցնելու։ Միայն առաքման ամրագրման հրաման ուղարկող աշխատողը հայտարարում է հրամանն ու թիրախ էությունը միասին՝

```haskell
Integration.TypedInbound
  '[ '(RecordShipmentBooking, ShipmentEntity)]
```

`RecordShipmentBooking`-ը և `ShipmentEntity`-ը հավելվածի տիպեր են։ Ելքերի ցանկը մատակարարի պատասխանների ցանկ չէ։ `Integration.TypedInboundConfig outputs`-ի `run` ֆունկցիան ստանում է պոլիմորֆ արձակման հետադարձ կանչ։ Յուրաքանչյուր արձակվող հրամանի համար այդ հետադարձ կանչը պահանջում է `AllowedOutput command outputs`, `Json.ToJSON command` և `KnownSymbol (NameOf command)`։ Թույլատրելի ելքի սահմանափակումը ստուգում է, որ հրամանի թիրախ էությունը համապատասխանի հայտարարված զույգին։

`Integration.typedInbound`-ը փաթեթավորում է կարգավորումը և պահանջում `KnownInboundOutputs outputs`։ Աշխատողը վերադարձնում է `Task IntegrationError Unit`։ Արձակման հետադարձ կանչն էլ վերադարձնում է `Unit`-ով Task։ Այն չի վերադարձնում ստացողի իրադարձությունների պատմությունը, հարցման տողը կամ տիպավորված բիզնես պատասխանը։

`Integration.asInbound :: TypedInbound outputs -> Inbound`-ը տիպավորված աշխատողը հարմարեցնում է հավելվածի գրանցման հին ձևին։ Տրամադրված `Timer.every`-ն արդեն վերադարձնում է հին ձևի `Inbound`։ Այս փոխակերպումը չի նշանակում, որ հնարավոր է հակառակ ուղղությամբ ժամաչափից ստանալ մոդելի վրա հիմնված տիպավորված աշխատող։ Գեներացված կարգավորումը ստուգելիս տիպավորված աշխատողի հայտարարություններն ու հին ձևի արժեքները տարբեր պահեք։

## Անվիճակ և ռեսուրս կառավարող ձևեր <a id="lifecycle" />

Առանց վիճակ պահելու ելքային մշակիչը իրադարձության համար վերադարձնում է գործողություններ՝ առանց մշակվող իրադարձությունների միջև կլիենտի կառավարվող վիճակ պահելու։ Թանկարժեք, վերօգտագործելի կապի համար `Integration.Lifecycle.OutboundConfig state`-ն առանձին ձեռքբերման, մշակման և ազատման hook-եր է տրամադրում՝

```haskell
initialize :: StreamId -> Task Text state
processEvent ::
  state -> Event Json.Value ->
  Task Text (Array Integration.CommandPayload)
cleanup :: state -> Task Text Unit
```

Սրանք կարգավորման դաշտերի ստորագրություններն են։ Դիսպետչերը վիճակը պահում է յուրաքանչյուր էության հոսքը սպասարկող աշխատողի համար և հերթով մշակում այդ աշխատողի իրադարձությունները և մաքրում անգործ աշխատողին։ Հետագա իրադարձությունը սկսում է նոր կյանքի ցիկլ։ Հում իրադարձությունն ինքնաբերաբար տիպավորված տվյալ կամ վերակառուցված էության վիճակ չի դառնում։

`Application.withOutboundLifecycle @() @MugOrderEntity (\_ -> config)`-ը գրանցում է կարգավորման ֆաբրիկա։ Այն տարբերվում է տիպավորված իրադարձության մշակիչի ուղուց։ Մուտքային աշխատողներն իրենց `run`-ի ներսում են ձեռք բերում ու ազատում ռեսուրսը. նրանց համար համապատասխան երեք hook-ով գրառում չկա։ [Կառավարեք ինտեգրման ռեսուրսները](/guides/integrations/resources/) էջը բացատրում է մասնակի ձեռքբերումը, չեղարկման նկատմամբ անվտանգ փոխանցումն ու մաքրումը։

## Ձախողում, կրկնափորձ և ավարտ <a id="errors" />

Գրանցված ադապտերի սխալների տարբերակներն են `TransportFailure Text`, `AuthenticationFailure`, `PermanentFailure Text`, `TransientFailure Text` և `ValidationFailure Text`։ Դրանց տեքստը անվտանգ պահեք հանրային ախտորոշման համար։ Ֆասադի սխալի տիպը տարբեր է։ Մոդուլների հասկացությունների նույնանման լինելը սխալի այս կառուցիչները փոխարինելի չի դարձնում։

Սխալի արժեքն ինքնին կրկնափորձ չի նշանակում։ Կրկնափորձի քաղաքականության համար պատասխանատու են ադապտերի իրականացումներն ու դրանք կանչողները։ Համաժամեցված մշակման ժամանակ առաջացած բացառությունների դեպքում դիսպետչերը կարող է փորձը կրկնել, իսկ վերադարձված տիպավորված Task սխալը առանձին ուղի է։ Հետևաբար մատակարարի գործողությանը պետք է տալ կայուն գործողության նույնացուցիչ և կրկնակի մշակման բացահայտ քաղաքականություն։ Դիսպետչերը համընդհանուր մեկանգամյա կատարում չի երաշխավորում։

Մուտքային աշխատողի վերադարձած ինտեգրման սխալի դեպքում հավելվածը աստիճանաբար երկարացվող դադարներով վերագործարկում է այն։ Սովորական ավարտը կանգնեցնում է աշխատողին։ Այս պայմանագիրը չի խոստանում վերագործարկել գործարկման միջավայրի բոլոր հնարավոր բացառություններից հետո։ Յուրաքանչյուր փորձին պատկանող ռեսուրսներն ազատեք, նախքան հաջորդ փորձը նորերը ձեռք կբերի։

### Մեկնարկ, կանգնեցում և սպասում <a id="await" />

Հավելվածի մեկնարկը կազմում է գրանցումները և սկսում ելքային դիսպետչերը։ Մուտքային աշխատողներն արձակելուց առաջ այն վավերացնում է հայտարարված տիպավորված ելքերը։ Կանգնեցման ժամանակ մուտքային առաջադրանքները չեղարկվում են, և դրանց ավարտին սպասվում է `AsyncTask.waitCatch`-ով։ Սպասումը շարունակվում է մինչև աշխատանքն ու դրա մաքրումն ավարտվեն։ Դանդաղ մաքրումը հետաձգում է ավարտը։

Ելքային դիսպետչերի կանգնեցումը սկսում է աշխատողների կանգնեցումը։ Դրա վերադարձը չի հաստատում, որ բոլոր աշխատողների ռեսուրսներն ազատվել են։ Հարկադիր չեղարկումն ու գործընթացի դադարեցումը կարող են մաքրման տարբեր արդյունքներ ունենալ։ Սպասող բիզնես աշխատանքը պահպանեք հավելվածի վիճակում, ոչ թե վերաբերվեք հիշողության մեջ պահվող կլիենտի կյանքի ցիկլին որպես առաքման գրառման։

`AsyncTask.waitFor`-ը, `waitCatch`-ը և `waitOutcome`-ը տարբեր սխալի տեղեկություններով հետևում են աշխատողի ավարտին, ինչպես մանրամասնված է [Առաջադրանքներ և կողմնակի ազդեցություններ](../../core/tasks/#async-task) էջում։ Հաջող մուտքային արձակումը նշանակում է, որ ստացող մշակիչը հայտնել է հրամանի ընդունման մասին։ Այն չի սպասում հետագա ելքային գործողություններին կամ հարցման վիճակի թարմացմանը։ Միայն աշխատողի ավարտը չի ապացուցում մատակարարի հաջողությունը կամ բիզնես աշխատանքի ավարտը։ Յուրաքանչյուր արդյունք ստուգեք այն սահմանին, որը պատասխանատու է դրա համար։
