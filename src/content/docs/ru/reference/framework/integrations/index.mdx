Принятый заказ на кружку может запустить запрос на доставку. Провайдер может забронировать отправление, но магазину всё равно нужна принимающая команда, чтобы записать этот результат. Интеграция связывает эти шаги, не перенося вызов службы доставки в решение по заказу.

Этот справочник продолжает темы [Модели событий и фичи](../) и [Задачи и эффекты](../../core/tasks/). Полную обёртку для провайдера показывает руководство [Создайте переиспользуемую интеграцию](/guides/integrations/create-reusable/). Контракты здесь помогут проверить, какую работу настроил агент, кто отвечает за преобразования и что на самом деле подтверждает завершение обработчика.

## От записанного события к следующему решению <a id="outbound" />

Приложение преобразует записанное событие о заказе в запрос провайдеру. Протоколом и декодированием отвечает переиспользуемый модуль доставки. Он расположен за пределами `src/MyShop` и не импортирует команды или сущности магазина. Преобразование результата бронирования в принимающую команду для отправления задаёт приложение.

<IntegrationContract />

Полученный ответ провайдера не означает, что бронирование прошло успешно. Успешное бронирование не означает, что команда для отправления принята. Получатель применяет собственное решение, а запрос об отправлении обновляется отдельно. Отказ этой команды не отменяет исходный заказ или действие провайдера.

## Действия, настроенные через ToAction <a id="actions" />

Фасад `Integration` предоставляет способ превратить конфигурацию в действие. Его использует предоставленный модуль `Integration.Http`:

```haskell
class ToAction config where
  toAction :: config -> Action

outbound :: ToAction config => config -> Action
batch :: Array Action -> Outbound
```

`outbound` преобразует одно значение конфигурации. `batch` собирает действия в значение `Outbound`, которое возвращает обработчик приложения. Для события `Integration.none` не возвращает действий. Эти функции описывают работу, а диспетчер выполняет её после того, как событие достигнет обработчика.

Автор интеграции может создать действие напрямую через этот контракт:

```haskell
action ::
  (ActionContext -> Task IntegrationError (Maybe CommandPayload)) ->
  Action
```

`ActionContext` предоставляет службы времени выполнения, включая зарегистрированную диспетчеризацию исходящих действий. Действие может не вернуть команду для приложения или вернуть одну закодированную полезную нагрузку команды. `Integration.emitCommand command` создаёт успешно завершённую задачу с этой полезной нагрузкой. `Integration.noCommand` возвращает отсутствие команды. Ни один из этих помощников не доказывает, что решение принимающей команды приняло её.

`Integration.makeCommandPayload` является чистой функцией кодирования. Для неё нужны `Json.ToJSON command` и известный `NameOf command`. Для диспетчеризации также нужен зарегистрированный получатель, который разрешает `InternalTransport`. Если существующая развернутая команда не имеет такого разрешения, введите новую идентичность команды, а не меняйте её зафиксированное объявление. Этот переход объяснён в руководстве [Безопасно добавьте фичу](/tutorial/change-safely/).

В HTTP-конфигурации обратный вызов `onSuccess` означает, что ответ получен. До создания успешной команды приложение или обёртка должны проверить статус и декодировать тело ответа. При анализе преобразования результатов различайте повторы HTTP-запроса, повторы диспетчера и отказ принимающей команды.

## Зарегистрированные адаптеры запросов <a id="adapters" />

В модуле [`Service.Integration.Adapter`](https://github.com/neohaskell/NeoHaskell/blob/414602b9510a92dfac647bc68d6afadfb594502c/core/service/Service/Integration/Adapter.hs) описан другой вариант. Импортируйте его с квалификатором, чтобы его класс `Integration` отличался от модуля фасада:

```haskell
import Service.Integration.Adapter qualified as Adapter
```

Экземпляр `Adapter.Integration request` выбирает тип `Adapter.Response request` и реализует такие методы:

```haskell
runReal :: request -> Task IntegrationError (Response request)
runFake :: request -> Task IntegrationError (Response request)
```

Здесь `IntegrationError` принадлежит `Service.Integration.IntegrationError`, а не фасаду. Класс адаптера не требует суперклассов для JSON-кодека или схемы. Каждая реализация сама отвечает за нужные её протоколу кодирование, декодирование и проверку. В справочнике [JSON и схемы](../../core/json/) эти задачи отделены от структурных метаданных и тестовых данных, написанных вручную.

Зарегистрируйте тип запроса при сборке приложения:

```haskell
Application.new
  |> Application.withIntegration @ShippingRequest
```

`ShippingRequest` обозначает тип запроса вашего адаптера. Для регистрации нужны экземпляр адаптера, информация о типах запроса и ответа во время выполнения и `TypeName.Inspectable request`. При запуске приложения она создаёт запись в реестре диспетчеризации. Регистрация не добавляет обработчик событий, не преобразует заказ в этот запрос и не задаёт принимающую команду.

`Service.Integration.ShimEmit.emit` получает этот реестр и запрос, затем возвращает `Task IntegrationError (Response request)`. При отсутствии регистрации он возвращает `PermanentFailure`, а не вызывает реального провайдера без уведомления. Реестр приложения доступен реализации действия через контекст действия.

### Выбор определяется зарегистрированным маршрутом <a id="selection" />

Диспетчер адаптера может связать `runReal` или `runFake` со значением `Selection`. При запуске приложения обрабатывается выбор интеграции и создаются эти функции. Это не означает, что все реализации `ToAction` используют реестр. В частности, предоставленная HTTP-конфигурация реализует действие самостоятельно, поэтому регистрация адаптера не заменяет вызовы этого клиента.

Явно реализуйте имитацию и напрямую проверьте выбранные ответы и ошибки. Схема не реализует `runFake`, а успешный прямой тест имитации не доказывает, что работающее приложение выбрало именно её. Чтобы проверить поведение провайдера, можно обратиться настоящим HTTP-клиентом к контролируемому локальному сервису без внешних учётных данных. Эту границу тестирования рассматривает руководство [Создайте переиспользуемую интеграцию](/guides/integrations/create-reusable/).

## Типизированные входящие команды <a id="inbound" />

Входящий обработчик считывает внешние данные и вводит команды в приложение. Переиспользуемая часть отвечает за чтение и декодирование, а приложение преобразует уведомление в команду. Если обработчик может отправлять только команду бронирования отправления, он объявляет вместе и команду, и целевую сущность:

```haskell
Integration.TypedInbound
  '[ '(RecordShipmentBooking, ShipmentEntity)]
```

`RecordShipmentBooking` и `ShipmentEntity` являются типами приложения. Список выходов не является списком ответов провайдера. У `Integration.TypedInboundConfig outputs` есть функция `run`, которая получает полиморфную функцию отправки. Для каждой отправляемой команды ей нужны ограничения `AllowedOutput command outputs`, `Json.ToJSON command` и `KnownSymbol (NameOf command)`. Ограничение для разрешённого выхода сверяет целевую сущность команды с объявленной парой.

`Integration.typedInbound` упаковывает конфигурацию и требует `KnownInboundOutputs outputs`. Обработчик возвращает `Task IntegrationError Unit`. Функция отправки команды тоже возвращает задачу со значением `Unit`. Она не возвращает историю событий получателя, строку запроса или типизированный ответ о бизнес-результате.

`Integration.asInbound :: TypedInbound outputs -> Inbound` адаптирует типизированный обработчик к старой схеме регистрации приложения. Предоставленная функция `Timer.every` уже возвращает `Inbound` старого API. Это преобразование не означает, что таймер можно преобразовать обратно в типизированный обработчик, связанный с моделью. При проверке сгенерированной настройки различайте объявления типизированных обработчиков и значения старого API.

## Варианты без состояния и с собственными ресурсами <a id="lifecycle" />

Обработчик исходящей интеграции без состояния возвращает действия для события и не сохраняет между событиями клиент, управляемый жизненным циклом. Для дорогостоящего повторно используемого соединения в `Integration.Lifecycle.OutboundConfig state` предусмотрены отдельные хуки получения, обработки и освобождения ресурса:

```haskell
initialize :: StreamId -> Task Text state
processEvent ::
  state -> Event Json.Value ->
  Task Text (Array Integration.CommandPayload)
cleanup :: state -> Task Text Unit
```

Это сигнатуры полей конфигурации. Диспетчер хранит состояние для каждого обработчика потока событий сущности, последовательно обрабатывает его события и очищает простаивающий обработчик. Следующее событие начинает новый жизненный цикл с инициализации. Сырое событие не является автоматически типизированными данными или восстановленным состоянием сущности.

`Application.withOutboundLifecycle @() @MugOrderEntity (\_ -> config)` регистрирует фабрику конфигурации. Эта регистрация отделена от маршрута типизированного обработчика событий. Входящие обработчики сами получают и освобождают ресурсы внутри `run`. Для них нет соответствующей записи с тремя хуками. В руководстве [Управляйте ресурсами интеграции](/guides/integrations/resources/) объясняются частичный сбой при получении ресурсов, безопасная при отмене передача ресурсов для очистки и освобождение.

## Сбой, повторная попытка и завершение <a id="errors" />

Для зарегистрированного адаптера предусмотрены варианты ошибки `TransportFailure Text`, `AuthenticationFailure`, `PermanentFailure Text`, `TransientFailure Text` и `ValidationFailure Text`. Убедитесь, что текст ошибок безопасен для публичной диагностики. У фасада другой тип ошибки. Даже если одноимённые понятия встречаются в обоих модулях, конструкторы ошибок не взаимозаменяемы.

Значение ошибки само по себе не планирует повторную попытку. За эту политику отвечают реализации адаптера и их вызывающий код. Диспетчер может повторно выполнить обработку после синхронного исключения, тогда как ошибка, возвращённая типизированной задачей, проходит по другому пути. Поэтому операции провайдера нужен стабильный идентификатор и явная политика обработки дубликатов. Диспетчеризация не гарантирует выполнение ровно один раз.

Если входящий обработчик возвращает ошибку интеграции, приложение перезапускает его с увеличивающейся задержкой между попытками. При нормальном завершении обработчик останавливается. Это не обещает перезапуск после любого исключения времени выполнения. Перед следующей попыткой освобождайте ресурсы, полученные предыдущей.

### Запуск, остановка и ожидание <a id="await" />

При запуске приложение собирает регистрации и запускает исходящую диспетчеризацию. Перед запуском входящих обработчиков оно проверяет объявленные типизированные выходы. При остановке приложения входящие задачи отменяются, а затем среда выполнения дожидается их завершения с помощью `AsyncTask.waitCatch`. Ожидание продолжается, пока не завершатся обработчик и его очистка. Медленная очистка задерживает завершение ожидания.

Остановка диспетчера исходящих действий запускает остановку обработчиков. Сам факт её завершения не подтверждает, что освободили ресурсы каждого обработчика. Принудительная отмена и завершение процесса могут привести к другим результатам очистки. Сохраняйте ожидающую бизнес-работу в состоянии приложения, а не считайте жизненный цикл клиента в памяти записью об отправлении.

`AsyncTask.waitFor`, `waitCatch` и `waitOutcome` сообщают о завершении обработчика с разной информацией об ошибках, как описано в разделе [Задачи и эффекты](../../core/tasks/#async-task). Успешная отправка входящей команды означает, что принимающий обработчик сообщил о её принятии. Она не дожидается исходящих эффектов или обновления состояния запроса. Одно лишь завершение обработчика не доказывает успех у провайдера или завершение бизнес-операции. Проверяйте каждый результат на соответствующей границе ответственности.
