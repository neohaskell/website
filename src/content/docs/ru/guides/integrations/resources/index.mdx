Чтобы забронировать отправление, может хватить одного HTTP-вызова. Прослушивание обновлений по отправлению может удерживать соединение открытым часами. В обоих случаях интеграции нужен владелец соединения, который открывает его, использует и закрывает после завершения работы.

## Клиент принадлежит жизненному циклу обработчика

Обработчик исходящей интеграции без состояния выполняет работу для каждого события, не сохраняя между вызовами клиент. Используйте этот вариант, если предоставленная интеграция уже управляет нужными ей ресурсами. Хуки жизненного цикла полезны, когда собственной интеграции нужен дорогостоящий клиент, соединение или интерпретатор, который смогут использовать несколько событий.

За этот второй вариант отвечает [`Integration.Lifecycle.OutboundConfig`](https://github.com/neohaskell/NeoHaskell/blob/414602b9510a92dfac647bc68d6afadfb594502c/core/service/Integration/Lifecycle.hs). Диспетчер создаёт обработчик для потока событий сущности и передаёт его инициализированное состояние каждому обработчику события. События этого потока обрабатываются последовательно. Для разных потоков могут создаваться разные обработчики, поэтому ресурс здесь не является единственным экземпляром на всё приложение.

Временной интервал, обозначенный скобкой, заканчивается, когда простаивающий обработчик удаляют и освобождают его ресурсы. Для следующего события потребуется новая инициализация. История событий сущности сохраняется при смене клиентских экземпляров. Клиент является ресурсом времени выполнения, а не источником, который определяет текущее состояние отправления.

## Три хука, один владелец ресурса

В конфигурации есть три поля. В этих сигнатурах `state` обозначает ресурс, возвращаемый при инициализации, например клиент доставки:

```haskell
initialize :: StreamId -> Task Text state
processEvent ::
  state ->
  Event Json.Value ->
  Task Text (Array Integration.CommandPayload)
cleanup :: state -> Task Text Unit
```

`Task error value` описывает работу, которая может завершиться ошибкой или значением. Здесь ошибки имеют тип `Text`; инициализация возвращает `state`, обработка события возвращает полезные данные команды, а очистка возвращает `Unit`, то есть не возвращает полезного значения. Создание `Task` не запускает работу. В руководстве [Задачи и эффекты](/reference/core/tasks/) выполнение рассмотрено отдельно от принятия бизнес-решения.

При инициализации передаётся идентификатор потока событий. Используйте его, если провайдеру нужен ресурс, привязанный к этой сущности. После успешной инициализации диспетчер сохраняет полученный ресурс и передаёт его в `processEvent` и `cleanup`. Это обычное состояние времени выполнения. Хуки не сохраняют его при перезапуске процесса.

В `processEvent` передаётся событие типа `Event Json.Value` без декодирования. Декодируйте события, которые понимает интеграция, и преобразуйте их во входные данные протокола. Возвращайте данные команд для отправки приложением, кодируя команду с помощью `Integration.makeCommandPayload`. Преобразование приложения должно остаться за пределами общего модуля клиента. Эта низкоуровневая запись жизненного цикла является отдельным вариантом типизированного исходящего обработчика из предыдущего руководства. Она не предоставляет автоматически типизированные данные события или восстановленное состояние сущности.

Очистка освобождает то, что вернула инициализация. Закройте клиент и остановите подчинённые задачи, которыми он управляет. Очистка должна быть короткой и безопасной при повторном вызове. Если инициализация открыла соединение, а затем завершилась ошибкой до возврата ресурса, она должна сама закрыть соединение. У диспетчера нет успешно полученного состояния для очистки. Такое же внимание требуется при последовательном получении нескольких ресурсов.

## Удаление простаивающего обработчика и остановка

Диспетчер периодически проверяет простаивающие обработчики. Удаление обработчика завершает время жизни его ресурса. Следующее событие создаёт новый обработчик и снова запускает инициализацию. Поэтому инициализация должна допускать несколько циклов для одной и той же сущности. Она должна открывать клиент, а не повторять бизнес-операцию бронирования отправления.

Зарегистрируйте этот вариант с помощью `Application.withOutboundLifecycle @() @MugOrderEntity (\_ -> config)`, где `config` имеет тип `Lifecycle.OutboundConfig`. Первый аргумент типа выбирает конфигурацию типа `()`, а фабрика игнорирует это значение. Если настройки поступают при запуске, используйте вместо него тип конфигурации приложения и создайте конфигурацию клиента на его основе. Добавьте нужный импорт и регистрацию в композицию приложения, не заменяя всю её настройку. Сохраните определения уже развернутых команд, событий и запросов. Если существующая развернутая команда-получатель не разрешает `InternalTransport`, хук может вернуть новую команду, как объяснено в руководстве [Безопасно добавьте фичу](/tutorial/change-safely/).

При обычной остановке обработчика вызывается очистка. Остановка диспетчера запускает остановку обработчиков, но сама по себе не доказывает, что все ресурсы уже освобождены. Принудительная отмена и завершение процесса тоже отличаются от штатной остановки. Не полагайтесь на очистку как на единственный способ узнать, ожидает ли отправление обработки или уже завершено.

Диспетчер может повторить обработку после ошибки события, поэтому для операции провайдера нужна явная политика обработки дубликатов. Ошибка очистки не может отменить принятый заказ на кружку или действие провайдера по бронированию. Храните в состоянии приложения устойчивый идентификатор операции и её ожидающий статус, используйте стабильный ключ идемпотентности провайдера, если он это поддерживает, и выясняйте исход операции, если ответ провайдера неизвестен. Только после этого решайте, считать ли повтор новой попыткой бронирования.

## Входящий обработчик сам получает нужные ресурсы

Входящая интеграция меняет направление работы: она ждёт данные от провайдера и отправляет команды приложению. Ресурсами она управляет внутри функции `run`. Для неё нет аналогичной записи с полями `initialize`, `processEvent` и `cleanup`.

И `Integration.InboundConfig`, и `Integration.TypedInboundConfig` передают в `run` функцию отправки. Типизированный вариант ограничивает команды и целевые сущности, которые можно отправить. Ни один вариант не предоставляет автоматически управляемое подключение к провайдеру. Обработчик должен получить соединение для чтения данных, запустить цикл чтения и закрыть соединение, когда цикл завершится или завершится с ошибкой.

Оберните работу с полученным ресурсом в `Task.finally release work`. Первым аргументом передаётся задача очистки. Она защищает выход из цикла чтения, включая отмену. Получение ресурса тоже должно обрабатывать частичный сбой и передачу полученного ресурса защищённой очисткой работы. Для производственных ресурсов нужен шаблон получения и освобождения, безопасный при отмене, чтобы отмена не произошла между получением ресурса и установкой его очистки.

Если входящий обработчик возвращает ошибку интеграции, приложение запускает его снова с увеличивающейся задержкой между попытками. Каждая попытка должна освободить полученные ресурсы до того, как следующая откроет новые. При нормальном завершении обработчик не запускается снова. Во время остановки приложения среда выполнения отменяет входящие задачи и дожидается их завершения с помощью `AsyncTask.waitCatch`. Ожидание включает завершение очистки. Если очистка зависнет навсегда, ожидание тоже может не завершиться.

## Освобождение ресурса и завершение работы с отправлением

Ожидание следующего уведомления является нормальной работой обработчика. Обработчик, отправивший `RecordShipmentBooking`, передал команду приложению. Если решение по команде отправления приняло бронирование и записало его, это и есть бизнес-результат для отправления. Эти наблюдения отвечают на разные вопросы.

Попросите агента отдельно проверить эти границы на контролируемых ресурсах. Для исходящей работы проверьте инициализацию, повторное использование, очистку простаивающего обработчика и повторную инициализацию одного потока, а также изоляцию между потоками. Включите ошибку обработки, частичный сбой при получении ресурса и остановку. Для входящей работы подсчитайте получение и освобождение ресурсов при нормальном завершении, ошибке, перезапуске и отмене, затем дождитесь завершения обработчика и убедитесь, что новые уведомления больше не приходят. Отдельно проверьте состояние отправления, не опираясь только на счётчики ресурсов.

Закрытое соединение доказывает, что ресурс освобождён. Оно не доказывает, что последнее уведомление приняли, что действие провайдера отменили или что ожидающая работа продолжится после перезапуска. Для этих результатов нужны собственные команды приложения, сохранённые факты и политика восстановления.
