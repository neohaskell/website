Провайдер доставки принимает запрос на бронирование и возвращает его результат. Ему не нужно знать, как магазин кружек записывает заказ, какой сущности принадлежит отправление или когда решение по отправлению должно отклонить изменение. Эти решения принадлежат приложению.

В руководстве [Рабочие процессы между сущностями](/concepts/event-driven-workflows/) принятый заказ на кружку приводит к работе с отдельной сущностью отправления. Здесь мы выносим часть, отвечающую за взаимодействие с провайдером, в модуль, который сможет использовать другое приложение. Это продвинутое руководство для уже существующего приложения. Вы должны уметь распознавать объявления команд, событий и `Feature`. Контракты, специфичные для интеграции, будут введены здесь.

Модуль для повторного использования отвечает за протокол провайдера. Приложение отвечает за оба преобразования: из своего события в запрос провайдеру и из результата провайдера в новую команду. Даже успешное бронирование должно пройти решение команды, принимающей результат, прежде чем приложение запишет факт об отправлении.

## Контракт вне магазина

Разместите общий код в `src/Shipping/Booking.hs`, за пределами `src/MyShop`. Он может импортировать модули NeoHaskell и утилиты провайдера, но не должен импортировать сущности, события или команды магазина. Иначе для бронирования отправления следующему приложению придётся зависеть от магазина кружек.

Возьмите [полный модуль Shipping.Booking](/examples/shipping-booking.hs) за основу и импортируйте его в приложение как `Shipping.Booking qualified as Shipping`. В его конфигурации HTTP не используется аутентификация, поэтому он может работать с контролируемым локальным провайдером. Для развернутого провайдера настройте требуемую им аутентификацию.

Следующие фрагменты показывают небольшую обёртку вокруг предоставленной интеграции `Integration.Http`. Они описывают контракты и места преобразований, а не целое приложение. `Request` и `Booking` являются типами, которые мы определяем в `Shipping.Booking`:

```haskell
data Request = Request {
  reference :: Text,
  quantity :: Int
} deriving (Generic)

instance Json.ToJSON Request

data Booking = Booking {
  status :: Text
} deriving (Generic)

instance Json.FromJSON Booking
```

Поле `reference` обозначает эту операцию провайдера, а `quantity` указывает, сколько предметов она включает. Ни одно из полей не содержит событие магазина или тип сущности. В реальном контракте провайдера добавьте сюда пункт назначения и остальные обязательные поля, а не передавайте всё событие предметной области в JSON.

`Generic` поддерживает используемые здесь обобщённые экземпляры кодеков. `Json.ToJSON` отвечает за кодирование запроса, а `Json.FromJSON` за декодирование ответа. Это разные задачи. Экземпляр `Schema.ToSchema` задаёт структурное описание. Сам по себе он не декодирует ответ, не проверяет все правила провайдера и не создаёт реалистичные тестовые ответы.

## HTTP-обёртка и её результат

Обёртка принимает URL провайдера, запрос и функцию, которую передаёт вызывающий код:

```haskell
request ::
  Text ->
  Request ->
  (Result Text Booking -> command) ->
  Http.Request command
```

Функция обратного вызова получает сообщение об ошибке или декодированное бронирование и возвращает команду. Параметр типа `command` позволяет каждому приложению выбрать свою команду, не заставляя модуль доставки импортировать её. Храните URL в конфигурации. Для контролируемого локального провайдера подойдёт адрес обратной петли; для развернутого провайдера нужны его фактический адрес и аутентификация.

Внутри обёртки создайте `Http.Request`, указав `method = Http.POST`, `body = Http.json input`, настроенный URL, а также явные параметры аутентификации, тайм-аута и повторных попыток. Прежде чем декодировать тело ответа, функция обратного вызова должна проверить HTTP-статус. Название предоставленного обратного вызова `onSuccess` означает, что ответ получен. Ответ 503 всё равно должен превратиться в неуспешный результат бронирования. Декодируйте принятый ответ с помощью `Json.decode @Booking response.body`. Если тело ответа некорректно, верните ошибочный результат, а не выдуманное бронирование.

Оба поля обратного вызова передают результат функции приложения:

```haskell
onSuccess = \response -> toCommand (decodeBooking response),
onError = Just (\_ ->
  toCommand (Err "Shipping provider could not be reached"))
```

Здесь `decodeBooking` является нашей функцией декодирования с проверкой статуса, а не функцией фреймворка. Отделяйте диагностику провайдера от сообщений для вызывающего кода. Не возвращайте учётные данные или исходное содержимое конфиденциального ответа. Осознанно выбирайте поведение повторных попыток и передавайте стабильный ключ идемпотентности, если это поддерживается протоколом провайдера. Повтор HTTP-вызова и повтор диспетчеризации приложения являются разными операциями. Ни одна из них не гарантирует доставку ровно один раз.

## Преобразования остаются в MyShop

Обработчик событий магазина создаёт `Shipping.Request` из принятого заказа и задаёт преобразование результата. В адаптированном фрагменте `event` содержит данные нового заказа, `request` является запросом провайдеру, а функция обратного вызова сохраняет идентификатор отправления, выбранный приложением:

```haskell
Shipping.request providerUrl request \result ->
  case result of
    Ok booking -> RecordShipmentBooking {
      entityId = event.shipmentId,
      status = booking.status
    }
    Err _ -> RecordShipmentBooking {
      entityId = event.shipmentId,
      status = "provider-failed"
    }
```

Эти иллюстративные поля команды принадлежат магазину. Результат провайдера не определяет, что магазину разрешено записать. Например, решение по отправлению может отклонить неизвестный статус, даже если провайдер уже оформил бронирование. Такой отказ не отменяет действие провайдера и событие о первоначальном заказе.

Оберните настроенный запрос в `Integration.outbound` и соберите его действие с помощью `Integration.batch` в исходящем обработчике приложения. Зарегистрируйте этот обработчик в `Feature`. Чтобы диспетчеризация интеграции могла передать результат, команда, принимающая его, должна разрешать `InternalTransport`, а её обработчик должен быть зарегистрирован. Если существующая команда-получатель уже развернута и не разрешает этот транспорт, добавьте новую идентичность команды и новый срез, а не редактируйте зафиксированное объявление. Также сохраните определения развернутых событий и запросов, как объяснено в руководстве [Безопасно добавьте фичу](/tutorial/change-safely/).

## Задачи внутри адаптера

Автору переиспользуемой интеграции нужно понимать и работу, которая выполняется под конфигурационными записями. `Task error value` описывает работу, которая может завершиться ошибкой `error` или значением `value`. Создание `Task` не запускает HTTP-вызов. В блоке `do` оператор `<-` передаёт успешное значение следующему шагу. Если ошибка не обработана, она не даёт выполнить последующие шаги. Среда выполнения запускает действия интеграции. В руководстве [Задачи и эффекты](/reference/core/tasks/) этот контракт рассмотрен отдельно от принятия или отклонения бизнес-решения.

Предоставленная HTTP-обёртка использует `Integration.ToAction`, чтобы превратить конфигурацию в действие. Контракт низкоуровневого типизированного адаптера запросов описан в модуле [`Service.Integration.Adapter`](https://github.com/neohaskell/NeoHaskell/blob/414602b9510a92dfac647bc68d6afadfb594502c/core/service/Service/Integration/Adapter.hs): экземпляр `Integration request` связывает запрос с типом `Response request` и реализует `runReal` и `runFake`. Каждая операция возвращает `Task` с типом ошибки адаптера `IntegrationError`. Он отличается от типа ошибки, который предоставляет фасад `Integration`.

При тестировании такого адаптера явно реализуйте детерминированную имитацию. Например, для одного выбранного запроса она может возвращать фиксированный ответ с бронированием, а для другого типизированную ошибку. Схема не реализует `runFake`. Прямые тесты имитации адаптера также не доказывают, что работающее приложение направляет через неё каждый запрос к провайдеру.

## Входящая работа имеет ту же границу ответственности

Во входящей интеграции переиспользуемый код считывает внешние данные и декодирует их. Приложение преобразует декодированное уведомление в свою команду. Оставьте это преобразование за пределами модуля чтения протокола, так же как исходящая обёртка оставляет преобразование результата магазина за пределами обработки HTTP.

Типизированный API входящих интеграций представляет разрешённые выходы как список пар «команда и сущность». Например, обработчик приложения с типом `Integration.TypedInbound '[ '(RecordShipmentBooking, ShipmentEntity)]` объявляет команду, которую он может отправить, и целевую сущность. `Integration.TypedInboundConfig` предоставляет обработчику функцию отправки, ограниченную этим набором. У команды должны быть экземпляры для её имени и кодирования JSON, а её сущность должна совпадать с объявленной парой. Эти проверки ограничивают выходные команды, но не доказывают, что команда-получатель примет каждое уведомление.

`Integration.asInbound` преобразует типизированный обработчик в значение регистрации приложения типа `Inbound` из старого API. Предоставленная функция `Timer.every` уже возвращает `Inbound` из старого API, а не создаёт типизированный обработчик. Если автор провайдера использует типизированное объявление на основе модели, ему следует сразу предоставить типизированный обработчик, а не обещать, что старый обработчик можно преобразовать обратно. Управляйте получением, отменой и освобождением ресурсов явно, как описано в руководстве [Управляйте ресурсами интеграции](../resources/).

## Тесты для других приложений

Тестируйте переиспользуемый модуль без импорта `MyShop`: проверьте кодирование запроса, декодирование принятого ответа, неуспешный статус, некорректный ответ и ошибку транспорта. Затем отдельно проверьте преобразования приложения, включая результат, который отклоняет принимающее решение. Контролируемый локальный HTTP-сервис позволит проверить эти случаи с настоящим клиентом без учётных данных и внешних эффектов. Проверяйте и состояние отправления, и принятие заказа, это разные результаты.

Храните переиспользуемый код и его тесты вместе, если добавляете их в [монорепозиторий NeoHaskell](https://github.com/neohaskell/NeoHaskell). Укажите контракт протокола, требования к аутентификации и проверенные случаи ошибок, чтобы другое приложение могло настроить модуль, не перенимая предметную область магазина. Пакеты Neo являются будущим направлением распространения. Сейчас код добавляют в монорепозиторий.
