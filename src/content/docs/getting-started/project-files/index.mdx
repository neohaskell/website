The Counter starter gives each part of its behavior a place in the source. We can find the condition that rejected a zero increment, the event an accepted increment produces, and the calculation behind the query's answer.

This page uses the unchanged project from [Create a project](../create-project/) and the behavior we tried in [Check your first response](../first-response/). The excerpts below are for reading beside your own files, not replacements to paste into them.

## The application and its feature <a id="the-application-and-its-feature" />

Open your project directory in your editor. Paths on this page start at the project root, the directory containing `neo.json`. Here is a selection of its files, focused on the increment:

```text
neo.json
src/
  App.hs
  Starter/Counter/
    Feature.hs
    Commands/
      IncrementCounter.hs
    Events/
      CounterIncremented.hs
    Event.hs
    Entity.hs
    Queries/
      CounterView.hs
tests/
  Decider/Counter/
    IncrementCounterSpec.hs
  Property/
    CounterReplaySpec.hs
  scenarios/
    counter-flow.hurl
```

These are actual starter paths, even if you chose a different project name. In `src/App.hs`, `appEventModel` assembles the application. Among its settings are the HTTP transport and the features to include:

```haskell wrap
EventModel.withTransport WebTransport.server
EventModel.features do
  counterFlow
```

The `counterFlow` definition is in `src/Starter/Counter/Feature.hs`. It groups the command and query slices under the feature `Counter flow` and chapter `Manage counters`. Within that chapter, the increment slice declares:

```haskell wrap
slice "Increment a counter" do
  entity @CounterEntity do
    command @IncrementCounter do
      produces @CounterIncremented.Event
```

This says which command belongs to the slice and which event it can produce. It doesn't contain the condition for accepting that command. That implementation lives in `Commands/IncrementCounter.hs`.

## The model in the graphical IDE <a id="the-model-in-the-graphical-ide" />

Neo's graphical IDE displays those relationships on a canvas. It opens a diagram file named `event-model.json` in the project root. The unchanged starter doesn't include that file, so use the <a href={`${import.meta.env.BASE_URL}examples/counter-event-model.json`} download="event-model.json">Counter diagram</a> supplied for this lesson. Save it in your project root with the exact filename `event-model.json`. This adds a diagram of the existing starter; it doesn't change the application code.

From that directory, run:

```sh
neo ide
```

Leave the terminal running and open [http://127.0.0.1:2323](http://127.0.0.1:2323) in a desktop browser. This is the IDE, separate from the running application's documentation at port `8080`. Counter itself doesn't need to be running to inspect the diagram.

Select **Counter flow** in the feature list. Under **Manage counters**, select **Increment a counter** to locate its slice. Use **Zoom In**, **Zoom Out**, and **Fit View** at the lower left to adjust the canvas. In the increment column, follow `IncrementCounter` down to `CounterIncremented`, then follow that event's connection to `CounterView`.

## The command and its accepted event <a id="an-increment-through-the-source" />

In `src/Starter/Counter/Commands/IncrementCounter.hs`, the command carries the two fields we sent from the browser:

```haskell wrap
data IncrementCounter = IncrementCounter {
  entityId :: Uuid,
  amount :: Int
}
```

`entityId` selects the counter and `amount` says how much to add. These field names are required by the command, not freely chosen example names. In the same file, `getEntityId` identifies the state to load, and `decide` evaluates the command against it. After checking that the counter exists, the decision reaches this condition:

```haskell wrap
if cmd.amount <= 0
  then Decider.reject "Amount must be positive"
```

`cmd` is the command being evaluated. The condition rejects zero and negative amounts with the message we saw in the browser. This excerpt ends before the `else` branch, which accepts a positive amount and produces a `CounterIncremented` event. This is where to inspect a proposed change to which amounts are allowed.

The event's data is defined in `src/Starter/Counter/Events/CounterIncremented.hs`:

```haskell
data Event = Event {
  entityId :: Uuid,
  amount :: Int
}
```

It retains which counter changed and by how much. The nearby `Event.hs` groups this event with `CounterCreated` and `CounterDecremented` as the possible variants of `CounterEvent`. The command carries an intention; the event carries the accepted fact.

## State updates and query answers <a id="state-updates-and-query-answers" />

`src/Starter/Counter/Entity.hs` defines `CounterEntity`, the state of one counter. An **entity** is the state a command acts on. Here, that means one counter's identifier, label, and value, rather than the whole list of counters.

Its `update` function applies events to that state. The increment case is:

```haskell wrap
CounterIncremented e ->
  entity {value = entity.value + e.amount}
```

`e` contains the event's data. The expression keeps the entity's other fields and adds the event's amount to its value. Rejection never reaches this increment case because it records no increment event. To review how an accepted fact changes state, inspect `update` rather than the acceptance condition.

`src/Starter/Counter/Queries/CounterView.hs` defines the query row. Its `combine` function takes the entity's state and supplies the fields the browser reads:

```haskell wrap
combine entity _maybeExisting =
  Update
    CounterView {
      counterId = entity.counterId,
      label = entity.label,
      value = entity.value
    }
```

These are the fields returned inside `items` by the list route and directly by the route for one identifier. The query maintains an answer from the entity's state; reading it doesn't run the increment decision again. A proposed change to the displayed fields belongs here.

## The behavior described by tests <a id="the-behavior-described-by-tests" />

`tests/Decider/Counter/IncrementCounterSpec.hs` checks the decision directly. Its zero-amount case constructs an increment with `amount = 0`, runs `decide`, and inspects the result:

```haskell wrap
case result of
  RejectCommand msg ->
    msg |> shouldBe "Amount must be positive"
  AcceptCommand _ _ ->
    fail "expected a rejection for a non-positive amount"
```

The test passes only when that command is rejected with the expected reason. The same file checks a missing counter and an accepted positive amount. Notice that the condition in `decide` covers both zero and negative amounts, while this particular test tries zero.

Other tests follow different parts of the flow:

| File under `tests/` | What it checks |
| --- | --- |
| `Property/CounterReplaySpec.hs` | Applying a creation event and generated positive increments leaves a value equal to their total. |
| `scenarios/counter-flow.hurl` | Through HTTP, create a counter, increment twice, decrement once, read value `1`, and reject creation with an empty label. |

The replay test checks the entity's calculation; the HTTP scenario checks several commands and a query together. Neither decides whether a proposed behavior is what your application needs. Compare the cases with your intended behavior, not only with the code an agent produced.

## Application source and regenerated files <a id="application-source-and-regenerated-files" />

Neo created both the application source and the files needed to build it. After creation, you and your agent maintain the behavior in `src/` and the test cases in `tests/`. Project settings belong in `neo.json`, as described in [Create a project](../create-project/).

Neo uses those settings, the selected framework revision, and the source files it discovers to regenerate `flake.nix`, `cabal.project`, and the project's `.cabal` file. In our example, that last file is `my-neo-app.cabal`; its name follows the project name. Hand-written changes in these build files can be replaced during regeneration. Maintain project settings and dependency choices in `neo.json`, covered by [neo.json and dependencies](../../reference/configuration/project/).

The IDE's `event-model.json` has a different purpose. It stores the diagram, including its grouping and layout. Changing a diagram label is not an implementation of a new command decision. Review the source condition and its test when the intended behavior changes.

For a read-only inspection with your agent, you can ask:

> Without changing any files, trace a zero increment through this Counter starter. Show me the rejection condition in Commands/IncrementCounter.hs, the accepted-event update in Entity.hs, and the test that checks zero is rejected. Explain how those pieces account for the unchanged query value.

Compare the answer with the small excerpts in your own files. The rejection condition and its test belong together; the entity update shows the change that rejection prevents.
