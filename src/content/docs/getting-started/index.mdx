An agent needs both a way to approach the work and accurate information about the code it will change. NeoHaskell supplies these separately: shared **skills** guide development tasks, while project guidance describes the APIs for the exact framework revision your application uses.

Use the project from [Create a project](./create-project/), open at its root directory containing `neo.json`. [Run the application](./run/) covers the first build, and [Find your project files](./project-files/) shows where Counter's behavior lives. You don't need to change Counter to prepare your agent.

## Workflow skills in the project <a id="install-agent-skills" />

A skill is a set of instructions your coding agent can load for a particular job. The [NeoHaskell skills collection](https://github.com/neohaskell/skills) includes guidance for understanding an application, implementing a feature, and checking its behavior. Installing it gives the agent those instructions; it doesn't add an ordering feature or change the running application.

Neo 0.18.0 includes an installer for this collection. From your project root, run:

```sh
neo skills setup --tool codex --ci
```

This selects Codex and installs the complete collection without interactive questions. Neo fetches the skills from GitHub, so it needs a network connection. Without a `--skill` filter, related skills and their supporting resources are installed together.

Neo also has installation targets for Claude Code, Kiro, and Cursor. The [collection's own installation instructions](https://github.com/neohaskell/skills#install) describe its separate installer for Claude Code and Codex. Use one installation route for your project; the command above uses Neo's built-in route.

In your editor, open `.agents/skills/neohaskell-feature-pipeline/SKILL.md`. If your editor hides directories beginning with a dot, open that path directly. The file starts with the skill's identity:

```yaml wrap
name: neohaskell-feature-pipeline
```

This is the name from the file's opening metadata. Below it, the instructions connect understanding the application, implementing a change, and verifying the result. The name lets you request that workflow explicitly. Its default scope includes the application's interface, so a task limited to backend behavior should say so.

Keep the installed project skills with your application's version-controlled files so another developer or agent has the same instructions. Treat later skill updates as a separate change you can review.

## Guidance for the code you have <a id="prepare-your-environment" />

Shared workflow instructions don't determine which NeoHaskell APIs your project has. That comes from the framework revision selected by your project settings, introduced in [Create a project](./create-project/#review-the-project-settings).

Open the root `AGENTS.md` in your editor. Neo's generated instruction points the agent to `.neo/agent-guidance/active.md` before changing NeoHaskell APIs. Open that file too. When guidance is available, its opening metadata includes:

```yaml
status: ready
```

The following `source-sha` field identifies the framework commit, and a link opens the corresponding guidance index. The long identifier belongs to your project's framework source; it is independent of the shared skills collection's version. Follow that index when you or your agent need an API definition.

Neo synchronizes this guidance during `neo build`, `neo run`, and `neo test`. If the index reports that guidance is unavailable, fix the source or network problem it names, then run `neo guidance retry` from the project root. Check the index again before asking the agent to implement an API change.

You can check that your agent is using both kinds of instructions with a read-only request:

> Without changing files, read AGENTS.md and .neo/agent-guidance/active.md. Report the framework revision and open its guidance index. Then read .agents/skills/neohaskell-feature-pipeline/SKILL.md and explain which instructions describe the APIs and which describe the development workflow.

Compare its answer with the files in your editor. Naming a skill and locating the matching API guidance are concrete checks you can make before giving the agent an implementation task.

## A first behavior to describe <a id="describe-a-first-task" />

For the mug shop from [The work behind the code](../introduction/), accepting an order commits mugs to the customer and reduces available stock. A useful first task states that promise and what must happen when the order cannot be accepted.

The request below is an example for when you begin the shop, rather than a change to make to Counter during setup. It limits the first implementation to backend behavior:

```text wrap
Use neohaskell-feature-pipeline for backend behavior only.
Let a customer order ceramic mugs in a requested quantity.
Accept only positive quantities when enough stock is available.
Record an accepted order as OrderPlaced and provide a query for remaining stock.
Reject other quantities without recording OrderPlaced or reducing stock.
Check acceptance, insufficient stock, zero, and negative quantities.
Keep payments, shipping, and a frontend outside this change.
```

`OrderPlaced` is the event name chosen for this example. The quantity is an input to the command, so the decision must check it even when a screen would normally prevent entering zero. Payments and shipping can become separate changes after this behavior works.

## Evidence for the result <a id="check-the-result" />

Before implementation, agree on cases that distinguish acceptance from rejection. Each row below is an independent example starting with the stock shown, rather than a sequence of orders:

Acceptance records `OrderPlaced`; every rejection below records no `OrderPlaced` and leaves stock unchanged.

| Stock before | Quantity | Result and stock after |
| --- | --- | --- |
| 3 mugs | 1 | Accept; 2 mugs |
| 0 mugs | 1 | Reject; 0 mugs |
| 3 mugs | 4 | Reject; 3 mugs |
| 3 mugs | 0 or negative | Reject; 3 mugs |

These numbers are example inputs, not required configuration values. Ask the agent to show the decision and its tests alongside the observed query answers. For rejection, inspect both the absence of an accepted-order event and the unchanged stock. A stock answer alone doesn't establish why an order was refused.

[Find your project files](./project-files/) used the same inspection pattern for Counter: read the rejection condition, the accepted event's state update, and the test beside the intended behavior. Technical checks can catch implementation mistakes; deciding whether these cases express the shop's promise remains your work.
