配送プロバイダーは手配依頼を受け取り、手配結果を返します。マグカップ店が注文をどう記録するか、どのエンティティが配送を所有するか、配送に関する判断がどの変更を拒否するかを知る必要はありません。そうした選択はアプリケーション側で行います。

[エンティティをまたぐワークフロー](/concepts/event-driven-workflows/)では、受理されたマグカップの注文をきっかけに、別の配送エンティティで処理が始まります。ここでは、別のアプリケーションでも再利用できるよう、プロバイダーとのやり取りをモジュールに切り出します。これは既存のアプリケーションを対象にした高度なガイドです。コマンド、イベント、フィーチャー宣言を見分けられることを前提とします。統合固有の契約は、このページの例で説明します。

再利用可能なモジュールはプロバイダーのプロトコルを担います。アプリケーション側では、イベントからプロバイダー入力への対応付けと、プロバイダー結果から新しいコマンドへの対応付けの両方を行います。手配が成功しても、アプリケーションが配送の事実を記録するには、受け取り側コマンドが判断で受理する必要があります。

## ショップの外に置く契約

汎用コードは`src/MyShop`の外にある`src/Shipping/Booking.hs`に置きます。NeoHaskellのモジュールやプロバイダー用のユーティリティはインポートできますが、ショップのエンティティ、イベント、コマンドはインポートしません。そうしないと、次に使うアプリケーションが配送の手配にマグカップ店へ依存することになります。

[Shipping.Bookingモジュールの全体](/examples/shipping-booking.hs)を出発点にして、アプリケーションから`Shipping.Booking qualified as Shipping`としてインポートします。このHTTP構成は認証なしで、制御下にあるローカルのプロバイダーに接続できます。デプロイ先のプロバイダーが必要とする認証を設定してください。

以下の抜粋では、用意されている`Integration.Http`統合を使った小さなラッパーを説明します。完全なアプリケーションではなく、契約と対応付けの箇所を示します。`Request`と`Booking`は`Shipping.Booking`で定義する型です。

```haskell
data Request = Request {
  reference :: Text,
  quantity :: Int
} deriving (Generic)

instance Json.ToJSON Request

data Booking = Booking {
  status :: Text
} deriving (Generic)

instance Json.FromJSON Booking
```

referenceはプロバイダーが行う操作を識別し、quantityはその操作に含まれる品目数を表します。どちらのフィールドにも、ショップのイベント型やエンティティ型は含まれません。実際のプロバイダー契約で配送先などの必須項目があれば、ドメインイベント全体をJSONとして渡すのではなく、ここに追加します。

`Generic`はここで使う汎用コーデックのインスタンスを支えます。`Json.ToJSON`はリクエストのエンコードを、`Json.FromJSON`はレスポンスのデコードを担います。これは別々の役割です。`Schema.ToSchema`インスタンスが提供するのは構造の説明です。それだけでレスポンスをデコードしたり、すべてのプロバイダー規則を検証したり、実際の応答に即したテストデータを生成したりするわけではありません。

## HTTPラッパーとその結果

このラッパーは、プロバイダーのURL、リクエスト、呼び出し元から渡される関数を受け取ります。

```haskell
request ::
  Text ->
  Request ->
  (Result Text Booking -> command) ->
  Http.Request command
```

コールバックはエラーメッセージかデコード済みの手配結果を受け取り、コマンドを返します。型変数`command`によって、配送モジュールがコマンドをインポートしなくても、各アプリケーションでコマンドを選べます。URLは構成に置きます。制御下にあるローカルプロバイダーならループバックURLを使えますが、デプロイ済みプロバイダーには実際のエンドポイントと認証が必要です。

ラッパー内では、`method = Http.POST`、`body = Http.json input`、構成済みのURL、明示的な認証、タイムアウト、再試行の設定を指定して`Http.Request`を構築します。レスポンスコールバックでは、本文をデコードする前にHTTPステータスを確認します。用意されているコールバック名`onSuccess`はレスポンスが届いたことを表すだけです。503レスポンスも、失敗した手配結果にする必要があります。受理されたレスポンスは`Json.decode @Booking response.body`でデコードします。本文が不正なら、架空の手配結果を作らずにエラー結果にします。

2つのコールバックフィールドを、アプリケーションの関数に合流させます。

```haskell
onSuccess = \response -> toCommand (decodeBooking response),
onError = Just (\_ ->
  toCommand (Err "Shipping provider could not be reached"))
```

ここでの`decodeBooking`はステータスを確認するために定義したデコーダーであり、フレームワークの関数ではありません。プロバイダーの診断情報と、呼び出し元に伝えるメッセージは分けてください。認証情報や機密性の高いレスポンス本文を返してはいけません。再試行の動作は意図を持って選び、プロバイダーのプロトコルが対応している場合は、安定した冪等性キーをプロバイダーに送ります。HTTP呼び出しの再試行とアプリケーションのディスパッチ再試行は別の操作であり、どちらも厳密に1回だけの配信を保証しません。

## 対応付けはMyShop側に置く

ショップのイベントハンドラーは、受理された注文から`Shipping.Request`を構築し、結果の対応付けを渡します。この例では、`event`は新しい注文のペイロード、`request`はプロバイダー入力です。コールバックは、アプリケーションが選んだ配送IDを保ちます。

```haskell
Shipping.request providerUrl request \result ->
  case result of
    Ok booking -> RecordShipmentBooking {
      entityId = event.shipmentId,
      status = booking.status
    }
    Err _ -> RecordShipmentBooking {
      entityId = event.shipmentId,
      status = "provider-failed"
    }
```

ここに示すコマンドのフィールドはショップ側のものです。プロバイダーの結果が、ショップに記録を許す内容を決めるわけではありません。たとえば、プロバイダーが手配を完了した後でも、配送の判断が未知のステータスを拒否することがあります。その拒否によって、プロバイダーの処理や元の注文イベントが取り消されるわけではありません。

構成済みのリクエストを`Integration.outbound`で包み、そのアクションをアプリケーションのアウトバウンドハンドラーで`Integration.batch`にまとめます。そのハンドラーをフィーチャーに登録します。統合のディスパッチで受信側へコマンドを届けるには、受信側コマンドが`InternalTransport`を許可し、そのハンドラーが登録されている必要があります。デプロイ済みの既存受信側がそのトランスポートを許可していない場合は、凍結済みの宣言を変更せず、新しいコマンド識別子とスライスを追加してください。イベントやクエリも保持する方法は[フィーチャーを安全に追加する](/tutorial/change-safely/)で説明しています。

## アダプター内のTask

再利用可能な統合を作るには、構成レコードの下で行われる処理も理解する必要があります。`Task error value`は、`error`で失敗するか、`value`で完了する処理を表します。Taskを構築しただけではHTTP呼び出しは実行されません。`do`ブロック内の`<-`は、次の手順で使う成功値を取り出します。コードが失敗を処理しない限り、失敗した時点で後続の手順は実行されません。ランタイムが統合アクションを実行します。[タスクと副作用](/reference/core/tasks/)では、業務判断の受理や拒否とは別の契約として説明しています。

用意されているHTTPラッパーは、構成をアクションに変換するために`Integration.ToAction`を使います。より低レベルな型付きリクエストアダプターには、[`Service.Integration.Adapter`](https://github.com/neohaskell/NeoHaskell/blob/414602b9510a92dfac647bc68d6afadfb594502c/core/service/Service/Integration/Adapter.hs)で定義された別の契約があります。`Integration request`インスタンスはリクエストに`Response request`を関連付け、`runReal`と`runFake`の両方を実装します。各操作はアダプターの`IntegrationError`型を持つTaskを返します。このエラー型は、`Integration`ファサードが公開するエラー型とは異なります。

このようなアダプターをテストするときは、決定的なフェイクを明示的に実装します。たとえば、選んだリクエストには固定の手配結果を返し、別のリクエストには型付きの失敗を返せます。スキーマは`runFake`の実装ではありません。アダプターのフェイクを直接テストしても、実行中のアプリケーションが渡されたすべてのプロバイダーにそのフェイクを使うとは証明できません。

## インバウンド処理も同じ所有境界に従う

インバウンド統合では、再利用可能なコードが外部入力の読み取りとデコードを担います。デコード済みの通知をコマンドに対応付けるのはアプリケーション側です。アウトバウンドラッパーでショップの結果の対応付けをHTTP処理の外に置くのと同じように、プロトコルを読む処理の外に対応付けを置きます。

型付きインバウンドAPIでは、許可する出力をコマンドとエンティティの組のリストで表します。たとえば、アプリケーションのワーカーが`Integration.TypedInbound '[ '(RecordShipmentBooking, ShipmentEntity)]`を返すなら、そのワーカーが発行できるコマンドと対象エンティティを宣言しています。`Integration.TypedInboundConfig`は、その集合に制限された発行関数をワーカーに渡します。コマンドには名前とJSONエンコードのインスタンスが必要で、対象エンティティも宣言した組と一致しなければなりません。これらのチェックで出力は制限されますが、受信側コマンドが通知を受理するかどうかまでは保証しません。

`Integration.asInbound`は、型付きワーカーを従来の`Inbound`登録値に変換します。用意されている`Timer.every`は最初から従来の`Inbound`を返すものであり、型付きワーカーを構築する関数ではありません。モデルに基づく型付き宣言を使うプロバイダー実装者は、従来のワーカーを型付きに戻せると約束するのではなく、型付きワーカーを直接公開してください。リソースの取得、キャンセル、解放には、[統合のリソースを管理する](../resources/)で説明するように、明確な所有者を定めます。

## 別のアプリケーションでも使えるテスト

`MyShop`をインポートせずに、再利用可能なモジュールをテストします。リクエストのエンコード、受理されたレスポンスのデコード、成功以外のステータス、不正なレスポンス、トランスポート障害を確認します。次に、アプリケーションでの対応付けを別にテストし、受信側の判断が拒否する結果も含めます。制御下にあるローカルHTTPサービスを使えば、認証情報や外部への影響なしに、用意された実クライアントでこれらを試せます。注文の受理とともに、配送の状態も確認します。この2つは別の結果です。

NeoHaskellモノレポにコードを提供するときは、再利用可能なコードとテストを一緒に置きます。プロトコルの契約、認証の要件、確認した失敗ケースを含めれば、別のアプリケーションがショップのドメインに依存せずに設定できます。Neo packagesは将来の配布方法として検討されています。現在の提供先は[NeoHaskellモノレポ](https://github.com/neohaskell/NeoHaskell)です。
