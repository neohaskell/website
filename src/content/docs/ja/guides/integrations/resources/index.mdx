配送の手配にはHTTP呼び出しが1回あればよいかもしれません。一方、配送状況の通知を待つ間、接続を何時間も開いたままにすることもあります。どちらも統合ですが、接続を取得し、使い、処理を終えるときに解放する所有者が必要です。

[再利用できる統合を作る](../create-reusable/)では、配送プロバイダーのプロトコルをマグカップ店から切り離しました。この高度なガイドでは、その境界にリソースの所有権を加えます。再利用可能なモジュールは引き続き`src/MyShop`の外に置き、アプリケーション側で注文イベントをプロバイダー入力に、プロバイダー結果を配送コマンドに対応付けます。

## クライアントの寿命はワーカーの稼働期間に従う

ステートレスなアウトバウンドハンドラーは、イベントごとに処理を構築し、呼び出しの間にクライアントを保持しません。用意された統合が必要なリソースをすでに管理しているなら、この方法を使います。独自の統合で高コストなクライアント、接続、インタープリターを複数のイベント間で再利用したい場合は、ライフサイクルフックが役立ちます。

[`Integration.Lifecycle.OutboundConfig`](https://github.com/neohaskell/NeoHaskell/blob/414602b9510a92dfac647bc68d6afadfb594502c/core/service/Integration/Lifecycle.hs)は、後者の方法を表します。ディスパッチャーはエンティティストリームごとにワーカーを作り、初期化した状態を各イベントプロセッサーに渡します。そのストリームのイベントは順番に処理されます。ストリームごとに別のワーカーを持てるため、ここで作るリソースはアプリケーション全体で1つだけのシングルトンではありません。

アイドル状態のワーカーが削除され、クリーンアップされると、そのリソースの稼働期間は終わります。後続のイベントでは新たに初期化します。クライアントが変わっても、エンティティに記録された履歴は残ります。クライアントはランタイムのリソースであり、配送状態の正式な記録ではありません。

## 3つのフックと1つのリソース所有者

構成には3つのフィールドがあります。以下のシグネチャでは、`state`は初期化によって返されるリソース値、たとえば配送クライアントを表します。

```haskell
initialize :: StreamId -> Task Text state
processEvent ::
  state ->
  Event Json.Value ->
  Task Text (Array Integration.CommandPayload)
cleanup :: state -> Task Text Unit
```

`Task error value`は、errorで失敗するか、valueで完了する処理を表します。ここではエラーは`Text`です。初期化は`state`を返し、イベント処理はコマンドペイロードを返し、クリーンアップは有用な結果値がないことを示す`Unit`を返します。Taskを構築しただけでは実行されません。[タスクと副作用](/reference/core/tasks/)では、業務判断の受理とは別に実行の仕組みを説明しています。

初期化はストリームIDを受け取ります。プロバイダーのリソースをそのエンティティ専用にする必要がある場合に使います。初期化に成功すると、ディスパッチャーは返されたリソースを保持し、`processEvent`と`cleanup`に渡します。リソースの状態は通常のランタイム状態であり、フックを使ってもプロセス再起動後まで永続化されるわけではありません。

`processEvent`に渡されるイベントは、生の`Event Json.Value`です。統合が扱うイベントをデコードし、プロトコル入力に対応付けます。アプリケーションがディスパッチするコマンドペイロードを返すには、`Integration.makeCommandPayload`でコマンドをエンコードします。アプリケーション側の対応付けは汎用クライアントモジュールの外に置きます。この低レベルなライフサイクルレコードは、前のガイドで扱った型付きアウトバウンドハンドラーとは別の方法です。型付きイベントペイロードや再構築済みのエンティティ状態が自動で渡されるわけではありません。

クリーンアップでは初期化が返したものを解放します。クライアントを閉じ、クライアントが所有する下位の処理を停止します。短時間で安全に再試行できるようにしてください。初期化中に接続を開いた後、返す前に失敗した場合、その接続は初期化自身で解放する必要があります。ディスパッチャーにはクリーンアップするための正常に返された状態がありません。複数のリソースを順に取得するときも、同じ注意が必要です。

## アイドル状態のワーカーの削除とシャットダウン

ディスパッチャーは定期的にアイドル状態のワーカーを確認します。ワーカーを削除すると、そのリソースの稼働期間は終わります。後続のイベントでは別のワーカーが作られ、初期化がもう一度呼ばれます。そのため、同じエンティティで初期化が何度行われても問題がないようにしてください。初期化ではクライアントを開き、配送の手配という業務処理を繰り返さないようにします。

`Application.withOutboundLifecycle @() @MugOrderEntity (\_ -> config)`でこの方法を登録します。ここでの`config`は`Lifecycle.OutboundConfig`の値です。最初の型引数はユニット型の構成を選び、ファクトリーはその値を無視します。起動時に設定を渡す場合は、代わりにアプリケーションの構成型を使い、その値からクライアント構成を作ります。アプリケーション全体の設定を置き換えずに、必要なインポートと登録を組み込みます。デプロイ済みのコマンド、イベント、クエリの定義は保持してください。既存のデプロイ済み受信側が`InternalTransport`を許可しない場合、このフックから新しい受信側コマンドを返す方法は[フィーチャーを安全に追加する](/tutorial/change-safely/)で説明しています。

通常のワーカー停止ではクリーンアップが呼ばれます。ディスパッチャーのシャットダウンは停止を開始しますが、その処理が返っただけでは、すべてのリソースが解放されたとは限りません。強制キャンセルやプロセス終了は、正常な停止完了とは異なります。配送が保留中か完了したかを示す唯一の記録として、クリーンアップに頼らないでください。

イベント処理が失敗するとディスパッチャーが再試行することがあるため、プロバイダー処理には重複への対処方針が必要です。クリーンアップの失敗で受理済みの注文が取り消されたり、プロバイダーの手配が元に戻ったりするわけではありません。業務処理の永続的な識別子と保留中の状態はアプリケーションの状態に保持します。プロバイダーが対応していれば安定した冪等性キーを使い、プロバイダーの結果が不確かな場合は、新たな手配として再試行する前に状況を照合します。

## インバウンドワーカーは自分でリソースを取得する

インバウンド統合は方向が逆で、プロバイダーからの入力を待ち、アプリケーションコマンドを発行します。そのリソースの稼働期間は`run`関数の中で管理します。`initialize`、`processEvent`、`cleanup`フィールドを持つ対応レコードはありません。

`Integration.InboundConfig`と`Integration.TypedInboundConfig`は、どちらも発行関数とともに`run`を渡します。型付きの方は、発行できるコマンドと対象エンティティを制限します。どちらもプロバイダー接続を自動で管理しません。ワーカー自身が入力接続を取得し、読み取りループを実行し、そのループが完了または失敗したときに接続を解放します。

リソースを取得して行う処理は`Task.finally release work`で囲みます。最初の引数はクリーンアップ用Taskです。これによりキャンセルを含め、読み取りループが終了するときに解放できます。取得処理自体も、部分的な失敗と保護された処理への引き渡しを扱う必要があります。本番環境のリソースでは、ハンドル取得後にクリーンアップを設定する前にキャンセルされないよう、キャンセルに安全な取得と解放のパターンを使います。

インバウンドのrunが統合エラーを返すと、アプリケーションはバックオフを入れてワーカーを再起動します。次の試行で代わりのリソースを取得する前に、各試行で取得したリソースを解放します。正常に完了したrunは再起動されず、終了します。アプリケーションのシャットダウンでは、ランタイムがインバウンドタスクをキャンセルし、`AsyncTask.waitCatch`で終了を待ちます。待機中にワーカーとクリーンアップの両方が完了します。クリーンアップが永久に止まらなければ、待機も終わりません。

## リソースの解放と配送の完了

次の通知を待つリスナーは、正常に稼働しています。`RecordShipmentBooking`を発行したリスナーは、コマンドを送信済みです。受け取り側の判断が手配コマンドを受理して記録すると、配送の業務上の結果が得られます。これらはそれぞれ別の問いに答えます。

制御下のリソースを使って、これらの境界を個別にテストするようエージェントに依頼します。アウトバウンド処理では、1つのストリームでの初期化、再利用、アイドル時のクリーンアップと再初期化に加え、ストリーム間の分離を確認します。処理の失敗、取得途中の失敗、シャットダウンも含めます。インバウンド処理では、正常終了、失敗、再起動、キャンセル時の取得と解放の回数を記録します。その後、タスクの終了を待ち、通知が追加で届かないことを確認します。リソースのカウンターとは別に、配送の状態も確認します。

ソケットを閉じたことから分かるのは、リソースが解放されたことだけです。最後の通知が受理されたこと、プロバイダーの処理が取り消されたこと、再起動後に保留中の処理が再開することは証明できません。こうした結果には、それぞれ専用のアプリケーションコマンド、保持される事実、復旧方針が必要です。
